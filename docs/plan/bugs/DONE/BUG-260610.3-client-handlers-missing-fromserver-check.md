# BUG-260610.3: Client message handlers don't verify the message came from the server

## Status: Fixed
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Handlers/NetworkMessagingHandler.cs`

## Description
Four client-side handlers ignore the `fromServer` flag of the secure message API:

- `ClientMsgModSettingsReceived` (:185) — forged `MsgModSettings` (40001) overwrites a victim client's `Mod.Settings` (range/multiplier/power limits → divergence from server, broken terminal clamps). A payload with `Welder` omitted (ProtoBuf `SkipConstructor=true` leaves it null) makes `AdjustSettings` NRE mid-way.
- `ClientMsgBlockStateReceived` (:204) — forged block state desyncs a victim's UI.
- `ClientMsgModCommandResponseReceived` (:229) — forged response pops arbitrary "Nanobars" chat lines or full mission screens on any player's screen.
- `MsgBlockSettingsReceived` client branch (:274-284) — forged block settings desync.

SE relays mod messages client→client through the server; that is exactly why the handler signature carries `fromServer`. The two newest handlers already guard correctly (`ClientMsgDebugStatsReceived` :383, `ClientMsgProfileSummaryReceived` :406: `if (!isSenderServer) return;`).

## Root Cause
Older handlers predate the `fromServer` guard pattern.

## Fix
Commit f0693ec on `fix/v2.5.6`. Added the guard as the first statement inside each handler's `try`, before deserialization (mirroring `ClientMsgDebugStatsReceived`/`ClientMsgProfileSummaryReceived`):

- `ClientMsgModSettingsReceived`, `ClientMsgBlockStateReceived`, `ClientMsgModCommandResponseReceived`: `if (!fromServer) return;`
- `MsgBlockSettingsReceived` (shared server+client handler): `if (!fromServer && !MyAPIGateway.Session.IsServer) return;` — clients only accept server pushes, while the server branch keeps accepting client messages (those legitimately arrive with `fromServer == false`). The server-side ownership check on that branch remains open as BUG-260610.2.
