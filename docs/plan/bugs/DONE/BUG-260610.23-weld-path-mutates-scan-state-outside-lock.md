# BUG-260610.23: Weld path mutates shared scan state (ChangeHash, TargetBlockData fields) outside the list lock

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `NanobotSystem.Welding.cs:293-359, 327, 567, 623, 641-642, 654, 687`

## Description
The BUG-135 refactor moved the weld work outside `lock (State.PossibleWeldTargets)`, but it still mutates shared state the locking convention protects:

- `State.PossibleWeldTargets.ChangeHash()` at Welding.cs:327 is a non-atomic `CurrentHash++` on a `long` (`Collections/HashList.cs:24-27`). It races the background scan's `CurrentHash = hash` in `RebuildHash()` (under the lock, `Scanning.cs:1182-1208`). A lost update means the weld-exhausted guard (`_weldExhaustedAtHash`), the delta-sync hash (`SyncBlockState.GetTransmit`), and UI change detection can all see a stale hash for a list that actually changed → "BaR idles although list changed" heisenbugs on DS.
- `targetData.Ignore`/`targetData.Block`/`targetData.Attributes` writes inside `ServerDoWeld` race the scan's ignored-block preservation pass, which reads `old.Ignore`/`old.Block` under the lock (`Scanning.cs:1185-1204`).

All other `ChangeHash()` call sites (Welding.cs:249, Grinding.cs:201, Collecting.cs:40, `RemoveGrindTargetByPosition`) are correctly inside the lock; these are the outliers.

## Root Cause
Post-weld bookkeeping not brought back under the lock when the weld work was moved out.

## Fix
Take the lock briefly around the post-weld `Ignore`/hash updates (microseconds; does not reintroduce the BUG-135 contention).

**Resolution:** commit e6f45d2 (BuildId 260610.36) on `fix/v2.5.6` - post-weld ChangeHash now under lock(State.PossibleWeldTargets) - it was a non-atomic increment racing the scan RebuildHash. The targetData.Ignore/Block field writes in ServerDoWeld stay unlocked deliberately: plain bool/reference writes cannot tear and at worst the scan preservation pass misses them for one cycle.
