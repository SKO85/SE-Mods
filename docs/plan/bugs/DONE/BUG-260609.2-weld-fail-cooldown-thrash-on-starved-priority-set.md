# BUG-260609.2: Weld fail-cooldown too short — starved high-priority blocks starve the rest

## Status: Fixed
## Severity: Medium
## Version: v2.5.5
## Found In: Player report (X4n01, 5 Jun 2026) — `NanobotSystem.Welding.cs` failure branch + `BlockFailureCooldownHandler`

## Description
A player reported that when the highest-priority blocks are missing materials,
the BaR keeps trying them and never welds lower-priority blocks that do have
materials. Their proposed workaround was a companion Programmable Block script
that temporarily disables high-priority block classes; their stated opinion was
to "weld until you can" and drop the priority lock.

Partial welding already works: `ServerFindMissingComponents` pulls whatever
components are available (welder inventory, then a single source walk) and starts
a transport if it obtained even one component, so a block is welded partially
with whatever is on hand. The line-346 failure branch only fires when **none** of
a block's missing components are available from any source.

## Root Cause
The weld loop welds one block per tick and re-iterates the priority list from the
top on every tick (a failed block clears its lock-on, so there is no forward
cursor). The only thing preventing the BaR from re-failing the same starved
top-priority block is `BlockFailureCooldownHandler`, whose default was 4s and
which is purely time-based (never cleared when components arrive).

- Small starved set: all blocks park within the 4s window → the loop advances and
  welds available lower-priority blocks. Works.
- Large starved set (e.g. 12+ armour blocks all needing one exhausted component —
  very common): by the time the BaR parks block N, block 1's 4s cooldown has
  already expired, so the top-of-list re-iteration hits it first again, re-pulls,
  re-fails. The BaR perpetually cycles the starved high-priority blocks and never
  reaches lower-priority blocks that have components. This is the reported stall.

## Fix
Raised `BlockFailureCooldownHandler.CooldownSecondsDefault` from `4` to `15`
(`Handlers/BlockFailureCooldownHandler.cs:31`). The failure branch only triggers
on genuine starvation (partial pulls start a transport and never reach it), so a
longer park is justified: 15s comfortably outlasts a full priority-list traversal
so starved high-priority blocks stay skipped long enough for the BaR to weld the
lower-priority blocks that do have components, while staying well under the 30s
max and short enough that the stall isn't noticeable once components arrive.

`SyncModSettings` default and the `BlockFailureCooldownSeconds` config min/max
both reference the constant, so they pick up the new default automatically.
Existing `ModSettings.xml` files keep their saved value until reset.

Docs updated: `Config/general-settings.md`, `Welding/index.md` (3 mentions of the
old `4` default). BuildId → 260609.2.

Considered but deferred: tying cooldown invalidation to source rescans
(`SourcesUpdated`) so starved blocks are re-tested only when inventory may have
changed. More robust for very large sets / fast tick rates, but more code; the
raised default covers the reported case. Revisit if reports persist.

Not adopted: the companion PB workaround (class-level `SetWeldEnabled` toggling)
— brittle heuristics, and a script-side band-aid rather than a mod fix.

BUG-016 (push-target full backoff).
