# BUG-261122.4: Filtered GetBlocks in the background scan is not guarded against grid changes — whole cluster scan lost

## Status: Fixed
## Severity: Low
## Version: v2.5.6
## Found In: PR #151 test log (Lejangt, dedicated server 1.211.018) — `NanobotSystem.Scanning.Block.cs:550`, `:631`, `:715`; caught in `NanobotSystem.Scanning.cs:620`

## Description
```
AsyncClusterScan exception: System.InvalidOperationException: Collection was modified; enumeration operation may not execute.
   at System.Collections.Generic.HashSet`1.Enumerator.MoveNext()
   at Sandbox.Game.Entities.MyCubeGrid.VRage.Game.ModAPI.IMyCubeGrid.GetBlocks(List`1 blocks, Func`2 collect)
   at SKONanobotBuildAndRepairSystem.NanobotSystem.AsyncAddBlocksOfGrid(...)
```
The three fat-block traversals call `cubeGrid.GetBlocks(list, _fatBlockFilter)` on the scan thread. A block
added or removed on the main thread at that moment throws; `AsyncClusterScan` logs it and drops the whole
cycle for the cluster. `SharedGridBlockCache.GetBlocks(grid)` has had a guard for this since BUG-149 (keep
the partial list); these filtered calls bypass it. More block churn (projections being built) makes it more
likely.

## Root Cause
BUG-149 guard only on the unfiltered helper.

## Fix
Fixed in BuildId 261122.3. New `SharedGridBlockCache.GetBlocks(grid, list, filter)` (`Caches/SharedGridBlockCache.cs:53`)
with the BUG-149 `InvalidOperationException` guard (keeps the partial list; profile line
`SharedGridBlockCache.GetBlocksFiltered` with `partial=`), used at the three call sites in `AsyncAddBlocksOfGrid`
(`NanobotSystem.Scanning.Block.cs:550,631,715`). The remaining raw `GetBlocks` (`Utils/UtilsProductionBlock.cs:28`)
runs on the main thread (PB `EnsureQueued`) and needs no guard.
Test: `ProjectorScanCacheTests.FilteredGetBlocks_GridChangedMidEnumeration_KeepsThePartialList`.

## Scenario
no scenario: thread race, not reproducible on demand; verified by the absence of the log line on a busy
build (harness S08 or a large projection).
