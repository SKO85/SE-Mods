# BUG-261023.6: PriorityFixed / CollectPriorityFixed only enforced in the terminal UI; PB script priority changes are not saved, synced or re-clustered

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-261023.1 #6 — `Terminal/Properties.cs:71,103,147,179,223,255` (Set* delegates), `Models/SyncBlockSettings.cs:627-656` (`AssignReceived`), `Handlers/NetworkMessagingHandler.cs:287-338`

## Description
Admins can lock the priority lists with `Welder.PriorityFixed` / `CollectPriorityFixed`. Only the
terminal buttons/switches check those flags. The scripting delegates `SetWeldPriority`, `SetWeldEnabled`,
`SetGrindPriority`, `SetGrindEnabled`, `SetCollectPriority`, `SetCollectEnabled` return the handler's
`SetPriority`/`SetEnabled` directly, so **any PB script** changes locked priorities (PB scripts run on the
server). A modified client can do the same with a crafted settings message — `AssignReceived` applies the
priority strings unconditionally (the sender access check passes for the block owner).

Separately, those script setters never write `Settings.WeldPriority = handler.GetEntries()` (the terminal
does): the change is not persisted, not synced to clients, and the cluster key hash (which hashes the
string) doesn't change — so a scripted priority change on a cluster member is ignored because the
coordinator scans with its own lists. No rescan is triggered either.

## Steps to Reproduce
1. `PriorityFixed = true` in ModSettings.xml.
2. PB: `welder.GetValue<Action<int,int>>("BuildAndRepair.SetWeldPriority")(0, 99);`
3. Priority changes despite the lock; reload the world → change lost.

## Root Cause
Policy check lives in UI predicates; script delegates bypass the settings write-through.

## Fix
Implemented (BuildId 261023.4).
- `NanobotSystem.cs`: six `ScriptSet{Weld|Grind|Collect}{Priority|Enabled}` methods. Each returns
  without changing anything while `Welder.PriorityFixed` (weld/grind) or `Welder.CollectPriorityFixed`
  (collect) is set; otherwise it mutates the handler and writes `Settings.*Priority =
  handler.GetEntries()` exactly like the terminal buttons — `Changed` → saved, transmitted, and
  `SettingsChanged` (cluster re-key + rescan) on the next update.
- `Terminal/Properties.cs`: the `BuildAndRepair.Set*Priority` / `Set*Enabled` PB properties return
  those methods instead of the raw handler setters.
- Server: `SyncBlockSettings.KeepLockedPriorities(received, current)` runs in
  `MsgBlockSettingsReceived` before `AssignReceived`; while locked, the client's priority strings are
  replaced by the current ones. Lists are kept as they are (not reset to default) — there is no
  "default priority" setting, and resetting would change existing BaRs the moment an admin locks.

Files: `NanobotSystem.cs`, `Terminal/Properties.cs`, `Models/SyncBlockSettings.cs`,
`Handlers/NetworkMessagingHandler.cs`.

Verification: unit — `PriorityLockTests` (7: write-through, all six setters ignored while locked,
collect lock independent, client-message matrix ×4). In-game: pending — SCN-PRIO-001 step 5 with and
without `PriorityFixed`; reload the world and confirm a scripted change persisted.
