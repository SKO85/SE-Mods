# BUG-260610.8: SharedEntityCache key is lossy — ignores box extents and the position hash collides

## Status: Fixed
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Caches/SharedEntityCache.cs:34, 81-98`

## Description
Two independent problems with the same symptom (wrong/missed entity results in BoundingBox mode):

1. The cache key is computed from the box **center** only (50 m quantized). Two consumers with centers in the same cell but very different extents — e.g. a 50 m solo box vs a multi-member cluster-union `discoveryBox` (`Scanning.Block.cs:814-826`) that can span kilometres — share one slot. Whoever queries first wins for 4 s: the large-box consumer receives the small box's entity list and silently misses every grid outside it. Co-located BaRs in different clusters (different settings → different cluster keys) make this recurring, and the slot thrashes.
2. `QuantizePosition` is `((17*31+qx)*31+qy)*31+qz` — a multiplicative hash, not the bit-packing the comment claims. Collisions are systematic: cells `(qx, qy+1, qz-31)` and `(qx, qy, qz)` produce identical keys, i.e. positions ~1550 m apart in Z share entity lists.

## Root Cause
Key omits extents; hash is non-injective despite coordinates fitting comfortably in 21 bits each.

## Fix
Commit 3a1e6d0 on `fix/v2.5.6`. `SharedEntityCache`:

- `QuantizePosition` replaced with `QuantizeToCells(Vector3D)` that genuinely bit-packs the three 50 m cell coords (21 bits each, exact for |coord| up to ~52,000 km) — used for both the box center and the half-extents.
- The slot key mixes `posKey` and `extentKey` (FNV-prime multiply + XOR), and `CachedEntityEntry` stores both keys; a hit requires `entry.PosKey == posKey && entry.ExtentKey == extentKey`, so a residual slot collision or a differently-sized box sharing a slot is a miss + overwrite — never wrong data.

Same-cell same-size consumers (the intended sharing case) still share one API call. BuildId → 260610.7. Build: Debug, 0 errors.
