# BUG-260610.21: MaxSystemsPerTargetGrid not enforced while BaRs are locked onto pre-materialization projected blocks

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Models/SyncBlockState.cs:186-195, 234-243`, `NanobotSystem.Operations.cs:489-496`, `NanobotSystem.Welding.cs:177, 207`

## Description
The limit check resolves projected blocks to the projector's **parent** grid id (BUG-164, `GetEffectiveGridId`), but the `CurrentWeldingBlock` setter increments `Mod.GridSystemCount` using `value.CubeGrid.EntityId` — for a not-yet-materialized projected block that is the **projected** grid id, a key no limit check ever queries. During the component-transport phase of projection welding (entire transport time per block, repeatedly), any number of BaRs can lock onto blocks of the same projection without counting toward `MaxSystemsPerTargetGrid` on the parent grid; the count only appears post-materialization when the target swaps to the physical block. With many BaRs and one blueprint this transiently but persistently bypasses the cap.

## Root Cause
Inc/Dec uses raw `CubeGrid.EntityId` while the checks use the effective (projector-parent) grid id.

## Fix
Commit 9a60711 on `fix/v2.5.6`. `NanobotSystem.GetEffectiveGridId` made `internal`; both lock-on setters now count by the effective (projector-parent) grid id — the same key every limit check queries. Two refinements beyond the ticket's minimum:

- The counted id is cached per lock-on (`_weldCountedGridId`/`_grindCountedGridId` in `SyncBlockState`) and the decrement always uses the cached key — without this, a projector closing mid-lock-on would change `GetEffectiveGridId`'s answer between Inc and Dec and leak a permanent +1 on the parent grid (GridSystemCount has no TTL). The BUG-160 count-once-per-grid rule is re-expressed on the cached ids (verified equivalent across all lock/move/release transition orders).
- The BUG-097 `samePhysicalBlock` identity check intentionally stays on RAW grid ids — projected→materialized swaps must still flip `Changed` for client sync.

Bonus: projected→materialized lock-on swap no longer Dec/Inc-churns the counter (both resolve to the parent id). CustomInfo's BUG-160 diagnostic now displays the count under the effective id so it matches the real counter key. BuildId → 260610.16. Build: Debug, 0 errors.
