# BUG-260610.14: Member saturated-skip blocks fresh members from applying an already-published scan result

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `NanobotSystem.Scanning.cs:131-138, 168-174`

## Description
The :131 bypass (BUG-260511.15) exists so a member behind the published result (`publishedResult.Timestamp > _lastAppliedResultTimestamp`) applies it immediately. But the member branch then unconditionally returns when `coordinator._scanSkippedSaturated` is true (:170-174) — including when the member has never applied any result (newly placed BaR joining a saturated cluster, or a member re-enabled after being off). The published result is valid and available, but the member is blocked from applying it until the coordinator performs a real scan — which, while saturated, only happens on forced rescan, coordinator exhaustion, or `MaxScanSkipDuration` (60 s, `NanobotSystem.cs:402`). Visible as "newly placed/enabled BaR does nothing for up to a minute".

## Root Cause
Saturated-skip check does not consider whether the member is behind the published result.

## Fix
Honor the saturated skip only when `publishedResult == null || publishedResult.Timestamp <= _lastAppliedResultTimestamp`.

**Resolution:** commit 422f124 (BuildId 260610.31) on `fix/v2.5.6` - member saturated-skip now applies only when there is no published result newer than _lastAppliedResultTimestamp - fresh/re-enabled members apply the published result immediately. Build: Debug, 0 errors.
