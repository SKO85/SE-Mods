# BUG-260610.16: PriorityHandling list mutated on main thread without _hashLock while background UpdateHash enumerates it

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Handlers/PriorityHandling.cs:281-307 vs 134-158, 178-189, 219-223, 248-273`

## Description
`GetPriority`/`GetEnabled` run on background scan threads and call `UpdateHash()` when `_HashDirty`. `UpdateHash` iterates `this` (the `List<>` base) under `_hashLock` — but the main-thread mutators (`Move` in `MoveSelectedUp/Down`, `SetPriority`, `SetEntries`, `Sort` in `ResetToDefaultOrder`) mutate the list **without** taking `_hashLock`. A player reordering priorities while a scan is in flight can throw `InvalidOperationException` (collection modified during enumeration) or produce a torn `_PrioHash` (block silently dropped from / misplaced in priority). The exception is swallowed by the worker `catch {}` (BUG-260610.15), so the symptom is a silently lost scan cycle.

## Root Cause
Mutators bypass the lock that protects the background enumeration.

## Fix
Take `_hashLock` in the mutators — they are cheap and rare (terminal UI interactions).

**Resolution:** commit 069ffaa (BuildId 260610.34) on `fix/v2.5.6` - all list mutators (MoveSelectedUp/Down, ToggleEnabled, SetPriority, SetEnabled, SetAllEnabled, ResetToDefaultOrder, SetEntries) take _hashLock, making them atomic vs the background UpdateHash enumeration. Build: Debug, 0 errors.
