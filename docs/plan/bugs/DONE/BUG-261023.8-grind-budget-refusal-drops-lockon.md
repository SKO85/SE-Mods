# BUG-261023.8: Grind-budget refusal releases the claim and drops the lock-on every refused tick

## Status: Fixed
## Severity: Low
## Version: v2.5.6
## Found In: REVIEW-261023.1 #8 — `NanobotSystem.Grinding.cs:182-185`

## Description
When `Mod.TryClaimGrindSlot()` refuses, the grind path releases the assignment and leaves
`currentGrindingBlock = null`, so `State.CurrentGrindingBlock` flips null/non-null on every budget-limited
tick: GridSystemCount dec/inc churn, `State.Grinding` flicker (sound/particle flicker in SP/listen
servers), and another BaR can take the block between ticks. The weld path keeps lock-on and assignment
on budget deferral (BUG-154).

## Steps to Reproduce
Many BaRs grinding one big grid with a low `MaxGrindsPerTick`; watch a BaR's grind effect flicker and `ServerTryGrinding` skipAssign churn.

## Root Cause
Budget-refusal branch copied the failure handling.

## Fix
Implemented (BuildId 261023.6), `NanobotSystem.Grinding.cs`: on `Mod.TryClaimGrindSlot()` refusal the
claim is kept and the chosen block is reported (`needGrinding = true`, `currentGrindingBlock =
chosen.Block`), exactly like the weld path (BUG-154). `MultiGrind` stops on the non-grinding result as
before; `State.CurrentGrindingBlock` and the grid count stay put, and the picker finds the same
self-claimed block first on the next tick. No unit test (needs the full grind loop); in-game: pending —
SCN-GRIND-004 with a low `MaxGrindsPerTick`.

## Scenario
SCN-GRIND-004 (budget refusal keeps claim and current block)
