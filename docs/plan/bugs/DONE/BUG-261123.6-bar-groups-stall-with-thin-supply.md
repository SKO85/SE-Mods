# BUG-261123.6: BaR groups stall when components are spread thin (capped pull miss parks blocks group-wide)

## Status: Done
## Severity: Medium
## Version: v2.5.7 (bug in v2.5.6 and earlier)
## Found In: REVIEW-261123.1 (profiler-driven performance review, 2026-11-23) — to investigate (weld budgets, per-grid limit, stagger, source rescans)

## Description
S103 (10 BaRs, 40 ship blocks) 12.8 welds/s; S104 (20 BaRs, 80 blocks) 4.5 welds/s; S108 (20 BaRs, busy base:
item traffic, docking, sorter) 2.6 welds/s. Plates are conserved in all, so it is throughput, not correctness. Runs were
at WorkSpeed 10 (S103 / S107 finished in ~3 s); rerun at WorkSpeed 3 (261123.24) for comparable numbers.

## Measured at WorkSpeed 3 (261123.24-261123.32)
| BaRs | Ship blocks | Welds/s quiet | Welds/s busy | ServerDoWeld / ServerTryWelding calls |
|---|---|---|---|---|
| 10 | 40 | 2.15 (S103) | 1.72 (S107) | 47 / 329 |
| 20 | 80 | 1.64 (S104) | 2.13 (S108) | 128 / 1,723 |
| 50 | 200 | 1.09 (S105, 197/200 in 180 s) | — | 648 / 16,880 (4 % of tries weld) |

Plates conserved everywhere (S105: 3,940 used = the 197 welded blocks' need); mod tick avg 0.013 ms, sim >= 0.98.
So not CPU: BaRs wait. The earlier "busy base halves throughput" came from the too-short WorkSpeed-10 runs and does not
hold at WorkSpeed 3. Hypothesis: plates spread thin (S105: ~16 per container over 302 containers, ~20 per block) ->
pulls collect too little, failed blocks are parked by the 15 s failure cooldown for the whole supply group, and more
BaRs means more contention on the same nearly empty containers. Next: `/nanobars test run S105 detail` — the
ServerTryWelding detail lines count skippedByFailCooldown / componentFailures / skippedByAssign / skippedByGridLimit.

## Root cause (S105 detail run, 261123.33: 200/200 in 248 s, 0.81 welds/s)
Not the idle-scan backoff: every BaR always had targets. Welds per 20 s fell 117 -> 28 -> 14 -> 12 -> 17 -> 3 -> ... -> 0
while the targets skipped by the failure cooldown were 61,000 / 46,000 / 30,000 per 20 s. A pull looks at 16 of the
351 sources (MaxSourcesPerPullWalk); 95 % of the sources it looked at were empty and ~2 of 3 pulls found nothing. Each
such miss parked the block for 15 s for every BaR on the conveyor network (BlockFailureCooldownHandler.MarkFailed),
although plates were still in the other 335 sources. As containers drain, misses rise, more blocks are parked: decaying
throughput, BaRs "Idle" with targets, worse with more BaRs (more unlucky looks). Exists in v2.5.6 (park was global).

## Fix
The park needs a full empty round: each BaR counts empty sources looked at since its last pick
(`_EmptyPullSourceVisits`, reset on a pick); a miss before the count reaches the source count only releases the block
and the BaR moves on, its round-robin cursor continuing with the next 16 sources. Pull cost per attempt unchanged; a
truly starved group parks after ~sources/16 looks per BaR (3 component failures per tick early exit still applies).
Files: NanobotSystem.cs (`NextEmptyPullVisits`, `IsPullRoundComplete`), NanobotSystem.Welding.cs.
