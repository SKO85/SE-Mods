# BUG-261122.16: Weld / grind targets are not range-checked when worked — a moving target is worked kilometres away

## Status: Fixed
## Severity: Medium
## Version: v2.5.6 (all versions)
## Found In: harness S66/S67 diagnostics (2026-11-22, BuildId 261122.26): maxTargetDistM 7537 m (area 200 m)

## Description
The area / range check runs only in the scan. A target whose grid moves (ship flying off, a ground-off piece of a
dynamic grid flung away) stays in the BaR's list and is worked until the next scan drops it (~5 s; longer when idle
backoff). S66 caught BaRs grinding a block 7.5 km away. Players can see a BaR grind a fleeing ship far outside its
area.

## Fix (proposed)
Before ServerDoWeld / ServerDoGrind (and collecting), a cheap execution-time check: block world position inside the
BaR's current area box (same test as the scan, `IsInRange(ref areaBox)`); out of range -> release, drop from the list,
pick the next. One position transform + box test per action, no allocation.

## Scenario
SCN-CORE-002 — ingame:S75 (welding), S76 (grinding): ship pushed out of the area mid-work, no change after leaving.

## Resolution
`IsTargetInArea` (same box as the scan) checked for the target chosen each cycle, before ServerDoWeld / ServerDoGrind;
out of area -> claim released, dropped from this BaR's list (next cycle picks the next). One transform + box test per
action, no allocation; `droppedOutOfArea` in the ServerTryWelding / ServerTryGrinding profiles. Collecting not changed
(floating objects are re-checked by their own transport path). BuildId 261122.27.
Verified in game, BuildId 261122.27: S75 / S76 — no integrity change after the ship left the area; S66/S67 farthest
held target 125 m (was 7.5 km).
