# BUG-260610.10: Projected blocks get the 15s global failure cooldown when they lose the proj-build budget race

## Status: Fixed
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `NanobotSystem.Welding.cs:542-553, 343-357`

## Description
When `ServerDoWeld` hits the BUG-107 gate (`Mod.TryClaimProjBuildSlot()`, global cap 3/tick) it returns `false` without marking the target as budget-deferred. Back in `ServerTryWelding`, if the component transport for that block has already completed (`transporting == false` — exactly the tick the block becomes buildable), control falls into the else branch (:343-357) which clears the lock-on (`State.CurrentWeldingBlock = null`), releases the assignment, and calls `BlockFailureCooldownHandler.MarkFailed(chosenTarget.Block)` — a **global** 15-second cooldown that makes every BaR skip the block (picker skip at Welding.cs:151-157). The cooldown handler's comment (`BlockFailureCooldownHandler.cs:28-30`) states "This branch only fires on genuine starvation," which the proj-build gate violates. Contrast with the `TryClaimWeldSlot` budget (:297-305), which preserves lock-on and defers gracefully. In multi-BaR shipyards with >3 projected builds landing in one tick, buildable blocks are continuously embargoed 15 s each, lock-ons/assignments churn, and projection throughput drops well below the budget's intent.

## Root Cause
The proj-build budget early-exit is indistinguishable from "can't weld" in the return path, so it lands in the starvation branch.

## Fix
Commit 1b900dd on `fix/v2.5.6`. New main-thread-only instance flag `_projBuildSlotDeferred` (declared in `NanobotSystem.cs` next to the weld-exhausted fields):

- Set in `ServerDoWeld` at the `TryClaimProjBuildSlot` rejection before `return false`.
- Reset at the call site immediately before each `ServerDoWeld` call.
- Consumed in `ServerTryWelding` by a new `else if (_projBuildSlotDeferred)` branch ahead of the failure branch: sets `needWelding = true` and `currentWeldingBlock = chosenTarget.Block`, preserving lock-on and assignment for a next-tick retry — exactly the handling the `TryClaimWeldSlot` budget path uses. No `MarkFailed`, no assignment release.

When the deferral coincides with an active transport, the `welding || transporting` branch already kept the lock-on; the stale flag is cleared by the pre-call reset. BUG-260610.35 (weld slot debited on proj-build rejection) remains open — accounting only. BuildId → 260610.8. Build: Debug, 0 errors.
