# BUG-260824.1: Components larger than the weld transport budget are never pulled (GitHub #141)

## Status: Fixed
## Severity: High
## Version: v2.5.6
## Found In: GitHub issue #141 validation — `NanobotSystem.Welding.cs`, `NanobotSystem.Init.cs`

## Description
GitHub issue #141: a small-grid BaR cannot repair blocks that need Radio Communication
or Detector components. Components placed in the BaR inventory are pushed back to cargo
("Push components immediately") and the repair never completes.

Both pull paths clamp the per-item amount with an integer floor against the remaining
*logical* transport volume budget:

- `TryPullFromSource` (`NanobotSystem.Welding.cs:1238`):
  `maxByVolume = (int)Math.Floor(remainingVolume / volume); if (maxByVolume <= 0) continue;`
- `ServerPickFromWelder` (`NanobotSystem.Welding.cs:1300`):
  `maxpossibleAmount = Math.Min(neededAmount, (int)Math.Floor(remainingVolume / volume));`

`remainingVolume` starts at `_MaxWeldTransportVolume = welderInventory.MaxVolume / 10 * WeldingMultiplier`
(`NanobotSystem.Init.cs:76-77`). On a small-grid BaR this budget is a few dozen litres.
Any component whose *single-item* volume exceeds the budget floors to 0 and is silently
skipped — it can never be pulled from sources nor picked from the welder's own inventory.

Affected vanilla components (unit volume): RadioCommunication 70 L, Medical 160 L,
GravityGenerator 200 L, LargeTube 38 L, PowerCell 40 L, SolarCell 20 L — whichever
exceed the local budget. On servers with a nerfed `WeldingMultiplier` (< 1) the budget
shrinks proportionally and more component types fall under the floor (which likely
explains Detector, 6 L, in the report).

Interaction that makes it visible: the block fails to weld → `BlockFailureCooldownHandler.MarkFailed`
parks it 15 s; meanwhile `ServerTryPushInventory` (5–10 s interval) pushes the manually
inserted component back out of the welder inventory — exactly the reported behavior.

## Steps to Reproduce
1. Small-grid BaR, survival, `WeldingMultiplier` 1 (or lower).
2. Damage a block that needs Radio Communication components below that component line (e.g. antenna).
3. Put the components in connected cargo or directly in the BaR; enable "Push components immediately".
4. BaR reports missing Radio Communication forever; inserted components bounce back to cargo.

## Root Cause
Per-pass transport volume budget floors to zero items for components whose unit volume
exceeds `_MaxWeldTransportVolume`; no minimum-one-item allowance. The *real* transport
inventory capacity (`welderInv.MaxVolume / BlocksInventorySizeMultiplier`) is much larger
than the logical budget, so allowing a single oversized item is safe.

## Fix
Both clamp sites now allow a single item when the transport inventory is empty:
`TryPullFromSource` gates on `_TransportInventory.CanItemsBeAdded(1, componentId)` before
forcing `maxByVolume = 1`; `ServerPickFromWelder` forces `maxpossibleAmount = 1` (existing
`CanItemsBeAdded` guard covers the real capacity). Commit 48de267, BuildId 260824.1.
Files: `NanobotSystem.Welding.cs`.
