# BUG-260610.24: DamageHandler.OnAfterDamage does an O(all BaRs) walk + faction-relation engine calls per grind-damage event

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Handlers/DamageHandler.cs:112-131`

## Description
Every grind damage event (ship and hand grinders emit these many times per second per grinder, server-wide) iterates the full `Mod.NanobotSystems` dictionary and calls `GetUserRelationToOwner` once per distinct welder owner — on the main simulation thread, with no throttle or per-(attacker,owner) result cache. On a busy server (dozens of BaRs/owners, several players grinding) this is hundreds of faction-relation engine calls per second. `FriendlyRelationsHandler.TryGetOwnersForOwner` already maintains exactly the needed owner-relation data on a 15 s rebuild.

## Root Cause
Per-event recomputation of relation data that is already cached elsewhere.

## Fix
Commit 36f40a3 on `fix/v2.5.6`. `OnAfterDamage` now calls `FriendlyRelationsHandler.TryGetOwnersForOwner(attackerId, ...)` — the exact owner set the old walk computed (welder-owners whose relation to the attacker is friendly), maintained by the existing 15 s rebuild — and marks friendly damage per cached owner. Zero engine relation calls and zero BaR iteration per damage event. The ≤15 s staleness window matches the bound already accepted for this data in BUG-260502.4 (friendly-damage TTL is 60 s). The now-unused `_seenOwnersBuffer` field was removed. BuildId → 260610.17. Build: Debug, 0 errors.
