# BUG-260610.18: CheckLimits doesn't clamp NaN or negative AreaSize/AreaOffset from clients

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Models/SyncBlockSettings.cs:696-728`

## Description
All clamps are one-sided `>` comparisons (e.g. `if (AreaSize.X > MaximumRange)`). NaN compares false against everything and negative values pass the upper-bound checks, so a forged `MsgBlockSettings` carrying `AreaSize = (NaN, NaN, NaN)` or negative components survives the server-side `SettingsChanged()` → `CheckLimits()` re-clamp, is persisted to entity storage and broadcast to all clients. `RecalcAreaBoundigBox()` then produces a NaN/inverted `BoundingBoxD` that poisons scanning. Same for `AreaOffset` (only `> MaximumOffset` / `< -MaximumOffset` checked — NaN passes).

## Root Cause
One-sided clamps; no NaN sanitation on float fields received from the network.

## Fix
Commit 7adb8fe on `fix/v2.5.6`. Sanitation block at the top of `CheckLimits` plus a `SanitizeFinite(value, fallback)` helper: non-finite `AreaOffset` components fall back to 0 (the existing two-sided ±MaximumOffset clamps then apply); non-finite `AreaSize` components fall back to `float.MaxValue` (clamped to `MaximumRange` by the existing checks) and all size components are floored at 1 m via `Math.Max`, so the bounding box can never invert. Runs on every load/receive path that calls `CheckLimits`. Related: BUG-260610.2 (sender validation, still parked). BuildId → 260610.13. Build: Debug, 0 errors.
