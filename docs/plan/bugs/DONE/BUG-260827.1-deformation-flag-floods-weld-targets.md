# BUG-260827.1: BUG-260824.7 regression — deformation flags flood the weld target list, welding stalls

## Status: Fixed
## Severity: Critical
## Version: v2.5.6
## Found In: In-game report after BuildId 260824.2 — `SlimBlockExtensions.cs`, `NanobotSystem.Scanning.Block.cs`

## Description
After the BUG-260824.7 fix, BaRs stop welding: state shows Idle, the terminal lists many
targets, transports repeat without any weld progress, and the game lags.

Root cause: BUG-260824.7 made the scan-path `NeedRepair` return true for blocks with
`MaxDeformation > MinDeformation`. That engine value is bugged and NEVER resets (the
original code comment warned exactly this), so on any grid that ever took deformation
damage the weld target list floods with full-integrity phantom blocks (hitting the
512-cap and crowding real weld/build targets out of `TruncateGridAware`). Every phantom
then fails `Weldable` in the weld loop — each check paying a `ResetSkeleton` engine call
(the lag) — so `needWelding` stays false → state Idle, nothing welds.

## Steps to Reproduce
1. BuildId 260824.2, grid with past collision/deformation damage plus real weld work.
2. Enable the BaR: target list fills, state Idle, transports repeat, no welding.

## Root Cause
Scan-side flagging of MaxDeformation-bugged blocks as weld candidates.

## Fix
- `NeedRepair` scan path reverted: `MaxDeformation > MinDeformation` is never a weld
  target again (`SlimBlockExtensions.cs`).
- New `Handlers/SkeletonResetHandler.cs`: the scan enqueues deformation-only blocks
  (integrity reached, dented, relation allowed, in range) for a budgeted main-thread
  `ResetSkeleton` (2/tick, per-block 60 s cooldown, dedup by grid+position) — dents
  still get repaired (the actual BUG-260824.7 goal) without entering the target list.
- Wired into `Mod.UpdateBeforeSimulation` (Process) and unload (Clear); added to csproj.

Commit 8e44747, BuildId 260827.1.
