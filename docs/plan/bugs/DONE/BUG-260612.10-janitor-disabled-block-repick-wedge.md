# BUG-260612.10: Janitor DisableOnly/HackOnly — freshly-disabled block re-picked every tick, burning the shared grind budget until next scan

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260612.1 #M3 — `NanobotSystem.Grinding.cs:116-121, 299-308, 325`, `NanobotSystem.Scanning.Block.cs:290-305`

## Description
`ServerDoGrind` grinds an Autogrind block down to `0.9 × criticalIntegrityRatio` — below the critical ratio. On every following tick the picker re-picks the same block: it sorts first (autogrind priority), isn't `IsFullyDismounted`, and the grind path has no Ignore flag and no failure cooldown (unlike welding's `BlockFailureCooldownHandler` parking). Each tick: claim assignment → consume a shared `TryClaimGrindSlot` count slot → early-exit at the janitor gate → release. The BaR does nothing else that tick and the wasted slots drain the fleet-wide grind count budget (5-10/tick). The scan rebuild evicts the block (~one scan round-trip via `TriggerImmediateRescan("grindComplete")`), but in janitor fleets this repeats after every disabled block.

## Root Cause
The janitor "done" condition exists only as a scan-side filter; the work-side early-exit leaves the entry live.

## Fix
On the DisableOnly/HackOnly early-exit, remove the entry from the local list (and propagate to cluster members, mirroring the dismount path) or park it via `BlockFailureCooldownHandler.MarkFailed`.

**Resolution:** commit 542b90b (BuildId 260612.13) on `fix/v2.5.6` - new _grindJanitorDone flag set at both janitor threshold early-exits; the caller treats it as completion and calls the new RemoveGrindTargetEverywhere helper (local removal + RebuildHash + BUG-260511.19 cluster propagation, also reused by the dismount path) — no more per-tick re-claim burning shared grind slots until the next scan.
