# BUG-261122.6: World-limit pre-check uses a different identity than the game's new check in proj.Build

## Status: Done (option B)
## Severity: Low
## Version: v2.5.7
## Found In: 1.211 IL check (2026-11-22) — `NanobotSystem.Welding.cs:654` (`_Welder.IsWithinWorldLimits`), `:712` (`proj.Build(..., builtBy: _Welder.OwnerId)`)

## Description
Before building, BaR asks `IMyShipWelder.IsWithinWorldLimits(projector, pairName, PCU)`. In the game that checks
the limits of the welder's **BuiltBy** identity (`MyShipWelder.IsWithinWorldLimits`: `TryGetIdentity(BuiltBy)`,
per-faction rule, owner relation). Since 1.211, `MyProjectorBase.BuildInternal` itself checks
`MySession.IsWithinWorldLimits(builtBy, limitType, PCU_CONSTRUCTION_STAGE_COST, ...)` for the `builtBy` argument,
which BaR passes as `_Welder.OwnerId` (BUG-115 history: the owner is the identity that is reliably resolvable).

When the BaR's builder and owner differ (ownership transferred, builder left the server, faction hand-over):
- owner over its limits, builder not → our check passes, the game refuses silently → counted as a silent fail
  (`reason=unknown`, `canBuild=OK` in the BUG-261122.1 log) and retried by BUG-261122.2;
- builder over its limits, owner not → we set `LimitsExceeded` and never try although the game would build.
Also the game uses the construction-stage PCU (1) in survival while we pass the full block PCU, so near the PCU
limit we refuse earlier than the game would.

## Steps to Reproduce
Not reproduced yet. Survival, block limits on: player A builds a BaR, transfers it to player B who is at the PCU
limit; projection in range → watch for `reason=unknown; canBuild=OK` in the log.

## Root Cause
Two different identities for the same decision; ModAPI only exposes the welder's BuiltBy-based check
(`IMySession` has no limit check for an arbitrary identity).

## Fix (proposed — decide after the diagnostics show it in the wild)
- Option A: pass the welder's `BuiltBy` as `builtBy` when it resolves to an existing identity, else fall back to
  `OwnerId` — both checks then use the same identity (changes who is charged the PCU of BaR-built blocks).
- Option B: keep `OwnerId`, and treat "pre-check passed but the game refused with `canBuild=OK`" as a limits
  signal (set `LimitsExceeded` / skip) instead of a generic silent fail.

## Scenario
SCN-WELD-002 (new step under limits: builder ≠ owner, owner at PCU limit).

## Resolution
Option B (owner decision 2026-11-23): blocks stay charged to the owner. `LimitsPreCheckApplies(builtBy, owner)`:
the welder pre-check runs only when builder == owner (and the builder is known); otherwise the game's own check in
proj.Build decides for the owner. A silent fail without the pre-check sets `LimitsExceeded` (terminal message) and
logs `reason=ownerLimitsLikely`. Not changed: the pre-check still uses the full block PCU (game: construction-stage
cost), low impact, unverified. BuildId 261123.5.
Testing: unit:LimitsPreCheckTests; in game S03 / S27 / S42 / S46 green on 261123.5 (normal case unchanged). The
transferred-BaR case itself has no scenario (needs world limits toggled mid-session; owner: skip).
