# BUG-260610.17: Per-client block-data request consumes the global dirty flag and delta hashes — other clients miss updates

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Handlers/NetworkMessagingHandler.cs:96-115`, `Models/SyncBlockState.cs:521-590`

## Description
Delta-sync state (`Changed`, `_lastTransmitted*Hash`, `_fullSyncCounter`, `LastTransmitted`) is stored once per block, not per recipient. When one client requests block data (`ServerMsgBlockDataRequestReceived`), the targeted `GetTransmit()`:

- sets `Changed = false`, so a change pending broadcast to everyone else is never broadcast (the periodic path gates on `IsTransmitNeeded()`); other clients keep stale state until the next change occurs;
- updates the list hashes, so the next broadcast to all other clients excludes lists those clients never received (corrected only after up to `FullSyncInterval` (5) further transmits, which themselves require new changes).

Real desync window, most visible for a BaR whose state changed once and then went quiet.

## Root Cause
Per-block delta-sync state shared across recipients; targeted sends mutate it.

## Fix
Commit f2bd418 on `fix/v2.5.6`. New `SyncBlockState.GetTransmitFull()`: resets the four lazy `_*Sync` lists and `ExcludedLists = 0` (intrinsically full snapshot) but does NOT touch `Changed`, the `_lastTransmitted*Hash` fields, or `_fullSyncCounter`; it only stamps `LastTransmitted` (time anchor for the receiver's transport math — sole side effect is delaying the next periodic broadcast by < 1 s). `MsgBlockStateSend` picks `GetTransmitFull()` when `steamId != 0` (targeted) and keeps `GetTransmit()` for broadcasts. The `ForceFullTransmit()` call in `ServerMsgBlockDataRequestReceived` was removed — the targeted send is now full by construction and must not poke the broadcast stream. BuildId → 260610.12.
