# BUG-261006.1: Lowered-limit lock-on release derives grid id from the block, not the counted id (GitHub #146 / PR #147)

## Status: Fixed
## Severity: Low
## Version: v2.5.6
## Found In: GitHub issue #146 + PR #147 by xmetisx (against v2.5.5) — `Mod.cs` `ReleaseSurplusLockOnsForLoweredLimit`

## Description
xmetisx reported (#146) and fixed (#147) a `GridSystemCount` leak in v2.5.5: the lock-on setters derived
the old grid id from `block.CubeGrid`, which is already null for a razed block, so the decrement was
skipped and grids slowly looked saturated. That leak was already closed on `fix/v2.5.6` by
BUG-260610.21 (setters decrement from the cached counted effective id) and BUG-260612.1 (self-subtract
compares against the same cached ids), so the PR's setter and Operations hunks are superseded.

One hunk of the PR still applied to our branch: `ReleaseSurplusLockOnsForLoweredLimit` (`Mod.cs:424-428`)
still read `CurrentWeldingBlock.CubeGrid.EntityId` / `CurrentGrindingBlock.CubeGrid.EntityId` to decide
which BaRs to release when an admin lowers `MaxSystemsPerTargetGrid`. Two misses: a razed lock-on
resolves to `0` and is never released, and a projected lock-on yields the projected grid id while
`overLimitGrids` is keyed by the effective (projector parent) id, so `Contains()` is false.

## Steps to Reproduce
1. 4 BaRs on one target grid, `MaxSystemsPerTargetGrid = 4`, one BaR locked onto a projected block.
2. `/nanobars config set MaxSystemsPerTargetGrid 2`.
3. The projected-lock BaR is not released (log line reports fewer releases than expected).

## Root Cause
Residual use of `block.CubeGrid` for grid-count bookkeeping after BUG-260610.21 moved the counting key to
`GetEffectiveGridId` cached in `State.WeldCountedGridId` / `GrindCountedGridId`.

## Fix
`Mod.cs` `ReleaseSurplusLockOnsForLoweredLimit`: `weldGridId` / `grindGridId` now read
`bar.State.WeldCountedGridId` / `GrindCountedGridId` — the exact `GridSystemCount` keys. BuildId 261006.1.
Credit: xmetisx (#146, #147). Not a leak fix on this branch (setters already decrement correctly), so no
behaviour change outside the admin lowered-limit path. PR #147 itself is not merged: it targets `main`
(v2.5.5) and would regress the effective-id counting.

## Scenario
SCN-CLUSTER-002 (step 3 "lower the limit mid-run" now covers projected and razed lock-ons).
