# BUG-261023.4: MaxPossibleWeldTargets doubled 512→1024 without a ticket or measurement

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-261023.1 #4 — `NanobotSystem.cs:50`, introduced in commit 14d3d25 (BUG-260827.2)

## Description
The BUG-260827.2 commit (transport-inventory fix) also raised `MaxPossibleWeldTargets` from 512 to 1024.
It is not mentioned in the ticket or commit message. The constant scales: the scan collection cap
(`Scanning.cs:490`, ×capMultiplier up to 4 → 4096), sort/cap and truncation work, per-member apply lists,
the weld-loop walk, the network hash, and the missing-components aggregate (BUG-261023.1) — all doubled.

## Steps to Reproduce
Compare `ApplyClusterResultToSelf`, `RebuildMissingComponentsAggregate` and `AsyncClusterScan` costs at 512 vs 1024 with S08.

## Root Cause
Diagnostic-session change left in.

## Fix
Implemented (BuildId 261023.3): reverted to the released value, `MaxPossibleWeldTargets = 512`.
- No reason for 1024 is recorded in commit 14d3d25 or BUG-260827.2, and v2.5.5 (512) is the baseline
  #143 was reported against; 1024 doubles the cluster collection cap (×4..16 → up to 16384), the
  per-member truncation, the weld loop walk and the missing-components aggregate.
- Trade-off: on projections larger than 512 buildable blocks per BaR, the missing-components list
  (BUG-260824.2) shows the need for the next 512 targets, not the whole blueprint. Raise it again
  only with an S08 measurement showing the cost is acceptable.

Files: `NanobotSystem.cs`; scenario text in SCN-CLUSTER-003, SCN-API-001.

Verification: build only. In-game: S08 (`test run S08 x5`) records the envelope at 512.

## Scenario
SCN-BUDGET-006 (S08 envelope at 512), SCN-WELD-005 (aggregate covers the capped list)
