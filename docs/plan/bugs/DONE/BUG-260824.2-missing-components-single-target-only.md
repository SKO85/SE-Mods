# BUG-260824.2: MissingComponents reports only the current weld target's shortfall (GitHub #142)

## Status: Fixed
## Severity: High
## Version: v2.5.6
## Found In: GitHub issue #142 validation — `NanobotSystem.Welding.cs`, `NanobotSystem.Operations.cs`, companion script

## Description
GitHub issue #142 ("pushing 0 to assemblers", same as closed #83): the companion script
queues tiny amounts (e.g. 6 PowerCell, 5 Electronics) to assemblers although hundreds are
needed for the blocks in range, and often queues nothing at all.

`State.MissingComponents` is cleared every work tick (`NanobotSystem.Operations.cs:115`)
and refilled only by `AddToMissingComponents`, whose sole caller is phase 3 of
`ServerFindMissingComponents(targetData, ref remainingVolume)` (`NanobotSystem.Welding.cs:1012`)
— and that runs for exactly ONE chosen target per tick (BUG-135 refactor captures a single
`chosenTarget`, `NanobotSystem.Welding.cs:264/338`).

In v2.2.x the weld loop kept iterating when a target could not be welded or transported,
calling `ServerFindMissingComponents` for every starved target in `PossibleWeldTargets`
until one welded — so `MissingComponents` was the aggregate shortfall over the whole
target list. The companion script (`Script.cs` `CheckAssemblerQueues` → mod
`UtilsProductionBlock.EnsureQueued`) queues exactly what `MissingComponents` reports,
so today it queues one block's shortfall at a time (a battery = a handful of PowerCell),
and the assembler trickles 5–6 items per welded block.

Compounding effects that produce the "0" in the title:
- A starved target is parked in the global 15 s failure cooldown
  (`BlockFailureCooldownHandler`); while every candidate is on cooldown, no
  `ServerFindMissingComponents` runs at all → `MissingComponents` is EMPTY.
- During the cosmetic transport timer, `ServerTryWelding` early-returns
  (`IsTransportRunning`) → cleared list is not refilled that tick either.
- The weld-exhausted hash skip (`_weldLoopExhausted`) also returns before any
  missing-component computation.

## Steps to Reproduce
1. Project/damage many identical blocks (e.g. 125 batteries) with no PowerCell stock.
2. Run the companion script with an assembler group.
3. Assemblers get queue jobs of ~one block's worth (or nothing while cooldowns hold).

## Root Cause
Missing-component aggregation was lost when the weld loop was refactored to a single
captured target per tick; the scripting API / terminal panel / companion auto-queuing all
consume `State.MissingComponents` assuming it covers all weld targets in range.

## Fix
New `ServerTryRebuildMissingComponentsAggregate` (NanobotSystem.Welding.cs) rebuilds
`State.MissingComponents` every 3 s as total need over all non-ignored weld targets at the
configured integrity level, minus stock in welder/transport/connected sources. Per-tick
`Clear()`/`RebuildHash()` and the per-target phase-3 reporting removed; called from
`ServerTryWeldingGrindingCollecting` (also clears when idle/welding disabled). Profiled via
`RebuildMissingComponentsAggregate`. Commit 48de267, BuildId 260824.1.
Files: `NanobotSystem.Welding.cs`, `NanobotSystem.Operations.cs`, `NanobotSystem.cs`.
