# BUG-260824.5: Transport-start condition fires on leftover transport items — phantom transports hold assignments

## Status: Fixed
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-260824.1 — `NanobotSystem.Welding.cs:939`

## Description
BUG-260612.2 changed `remainingVolume` to start at `_MaxWeldTransportVolume - CurrentVolume`,
but the transport-start test is still `remainingVolume < _MaxWeldTransportVolume`, which now
fires when leftover items sit in the transport inventory even though the current pass picked
nothing.

Failure: welder block full → `ServerEmptyTransportInventory` can only move `MaxItemsAddable`,
leftovers remain (`CurrentVolume > 0`). BaR targets a block with unavailable components:
`ServerFindMissingComponents` picks nothing but the condition is already true at entry →
phantom transport starts, returns `transporting=true` → caller's `else if (welding || transporting)`
(`Welding.cs:372`) keeps the lock-on and never reaches the failure branch (assignment release,
`MarkFailed`, starvation early-exit) → perpetual phantom transport cycles on one unweldable
block while holding its assignment so other BaRs skip it.

## Root Cause
Start-of-pass baseline changed without updating the "did this pass pick anything" comparison.

## Fix
`entryRemainingVolume` captured at pass entry; transport starts only when
`remainingVolume < entryRemainingVolume` (this pass actually picked something).
