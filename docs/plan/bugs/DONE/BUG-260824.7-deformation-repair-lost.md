# BUG-260824.7: Deformation-only repair silently lost — dents on full-integrity blocks never fixed

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260824.1 — `Extensions/SlimBlockExtensions.cs:49`, `NanobotSystem.Scanning.Block.cs:231`

## Description
`NeedRepair` with the scan's `allowMutate=false` neither resets the skeleton nor returns true
for full-integrity deformed blocks (`MaxDeformation > threshold`, integrity fine), and the
only `allowMutate=true` call site (`Welding.cs:478`) is reachable only for blocks already in
the target list.

Failure: an armor block at full integrity gets dented by collision. Old code: every ~2 s scan
called `ResetSkeleton` and visibly removed the dent. New code: the scan returns false without
resetting → block never enters the weld list → the weld-loop mutating call never runs for it
→ permanent deformation; the BaR no longer repairs dents at all (no other `ResetSkeleton`
caller exists).

## Root Cause
BUG-260610.5 moved the skeleton-reset side effect out of the background scan (correct —
main-thread-only engine call) but no main-thread path picks these blocks up.

## Fix
`NeedRepair` with `allowMutate=false` (scan) now returns true for the MaxDeformation
case instead of dropping the block — the block enters the weld list and the weld
loop's mutating call performs `ResetSkeleton` on the main thread (matches pre-
BUG-260610.5 behavior at ~2 s cadence). Commit 81561a9, BuildId 260824.2.
File: `SlimBlockExtensions.cs:47`.

**Regression note (2026-08-27):** flagging MaxDeformation blocks in the scan flooded
the weld target list with unweldable phantoms (welding stalled, lag). Superseded by
BUG-260827.1: scan enqueues dents to the new SkeletonResetHandler instead.
