# BUG-261122.8: ShowArea on moving BaRs reported to drop server performance — not reproduced on the mod side

## Status: Done (mitigation; reporter details still open)
## Severity: Medium
## Version: v2.5.6
## Found In: player report via the owner (2026-11-22) — `NanobotSystem.Update.cs:45-63` (per-frame area box draw)

## Description
A server's performance dropped when players enabled ShowArea on BaRs on moving grids.

## Measured (harness S28-S33, 01_211_018, SP, 5 BaRs, 60 s each, BuildId 261122.8)
Station / ship standing still / ship drifting 20 m/s with yaw, each with ShowArea off and on:
- Mod tick avg 0.010-0.014 ms, peak 0.17-2.2 ms, sim speed 1.00 in all six; scans 9, cluster rebuilds 30,
  entity queries 18 in all six; all 20 blocks repaired in all six.
- `ShowAreaDraw` (new profiler marker): 0.004 ms per BaR per frame (18905 calls / 60 s for 5 BaRs).
- The flag is not in the cluster key (`ScanClusterCoordinator.ClusterRelevantFlags`), and the box is only drawn
  where `!IsDedicated` — a dedicated server never draws it.

## Root Cause (hypothesis)
Render side, not mod CPU: every BaR with ShowArea submits a solid, semi-transparent box the size of its working
area (up to 200 m) every frame (`MySimpleObjectDraw.DrawTransparentBox(..., Solid, ...)`). Many overlapping
large transparent boxes are fill-rate (GPU) work on every machine that renders — on a listen (player-hosted)
server that is the server itself. Motion itself adds no mod work (measured). Not verifiable with the harness
(no GPU/frame-time metric).

## Questions for the reporter
Dedicated or player-hosted server? Server sim speed or client FPS? How many BaRs had ShowArea on, which area sizes?

## Fix (proposed, pick after the answers)
- Draw wireframe edges instead of a solid fill (`MySimpleObjectRasterizer.Wireframe`), or a much lower alpha.
- Distance cull: skip the box when the camera is farther than e.g. 2× the area size.
- Cap the number of boxes drawn per client per frame (nearest first).
- Optional admin lock already exists: `Welder.ShowAreaFixed`.

## Scenario
SCN-BUDGET-007 (S28-S33, measurement; add a GPU-side check manually: FPS with 20 overlapping boxes).

## Analysis (2026-11-23)
Far boxes cover few pixels and are cheap; the expensive case is a camera **inside** the area: its transparent faces
cover the whole screen, once per box (BaRs on a ship the player pilots: inside every box). Distance culling alone
would not help that case.

## Fix
`GetAreaDrawMode`: camera inside the area box (oriented, offset area) -> edges only (wireframe, brighter); outside ->
solid as before; more than 1000 m from the box surface -> not drawn. One transform (3 dot products) + clamp per BaR
per frame. `ShowAreaDraw` profile logs the mode. Edge width 0.01 m (0.04 / 0.02 looked too heavy in game). BuildId 261123.4.

## Testing
unit:AreaDrawModeTests (inside / outside / cull distance / rotated + offset area). In game by eye: fly into a BaR's
area -> fill disappears, edges stay; fly out -> solid again; ship with several BaRs (ShowArea on) piloted from inside.

## Resolution
Inside/outside draw mode as above. Verified by the owner in game, BuildId 261123.4: solid from outside, thin edges from
inside, rotated / offset areas switch at the visible boundary. No effect on dedicated servers (they never draw); helps
the frame rate of clients and of the host of a player-hosted server when the camera is inside BaR areas.
