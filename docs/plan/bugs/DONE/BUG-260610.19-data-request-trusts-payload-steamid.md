# BUG-260610.19: Server replies to client-supplied SteamId instead of tamper-proof sender in data requests

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Handlers/NetworkMessagingHandler.cs:86-94, 96-115`

## Description
`ServerMsgDataRequestReceived` and `ServerMsgBlockDataRequestReceived` reply to `msgRcv.SteamId` (client-controlled payload) rather than the tamper-proof `sender` argument. A forged request can direct settings/state payloads at arbitrary third-party players (unsolicited traffic / amplification), and — combined with BUG-260610.17 — another player can trigger the dirty-flag consumption "for" someone else. The command handler already uses `sender` correctly (`ServerMsgModCommandReceived` :131); these two should too.

## Root Cause
Payload field trusted where the transport-provided sender id is available.

## Fix
Commit 4ed2cf5 on `fix/v2.5.6`. Both handlers now reply to the tamper-proof transport `sender`: `ServerMsgDataRequestReceived` no longer even deserializes the payload (it carried only the SteamId), and `ServerMsgBlockDataRequestReceived` uses `sender` for both targeted sends and the unknown-system log line (payload `EntityId` is still read, as it must be).
