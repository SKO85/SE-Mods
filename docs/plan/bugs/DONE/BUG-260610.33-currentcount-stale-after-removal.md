# BUG-260610.33: HashList.CurrentCount stale after in-place removals

## Status: Fixed
## Severity: Low
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Collections/HashList.cs:24-27`, `NanobotSystem.cs:148-167`, `NanobotSystem.Grinding.cs:197-203`

## Description
`ChangeHash()` bumps the hash but not `CurrentCount`; only `RebuildHash()` refreshes it. `RemoveGrindTargetByPosition` and the post-grind removal therefore leave `CurrentCount` higher than the actual list size until the next scan. Consumers (`isIdleNoWork` at `Operations.cs:64-66`, the saturation-rebuild gate at `Operations.cs:119-122`, profiler/customInfo counts) read a too-high value — they only lose the idle fast-path, never skip real work, so impact is perf noise.

## Root Cause
`ChangeHash` is a hash-only bump; removal sites use it where the count also changed.

## Fix
Call `RebuildHash()` instead of `ChangeHash()` at the removal sites — they are already under the lock and run at low rates.

**Resolution:** commit 404c481 (BuildId 260610.22) on `fix/v2.5.6` - both in-place removal sites (RemoveGrindTargetByPosition, post-grind removal) call RebuildHash() instead of ChangeHash() so CurrentCount tracks removals; both already hold the lock. Build: Debug, 0 errors.
