# BUG-260610.13: ScanCluster.Members mutated on main thread while background scans iterate it

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Cluster/ScanClusterCoordinator.cs:87-113`, `NanobotSystem.Scanning.cs:437, 463, 479-488, 621`

## Description
`ScanCluster.Members` is a plain `List<NanobotSystem>`. `RebuildClusters()` runs on the main thread every ~2 s and *reuses* cluster objects across rebuilds (`cluster.Members.Clear()` then `Add()`; clusters only removed when empty). `AsyncClusterScan` runs on the background pool and reads `cluster.Members.Count` three separate times (:437, :463, :479) plus indexed access `Members[i]` (:481). Consequences:

- `ArgumentOutOfRangeException` if the list shrinks between the `i < Count` check and `Members[i]` — the :437/:463 reads are outside the inner try (:448), so this propagates into the worker and is silently swallowed (scan lost).
- Inconsistent decisions: `memberCount`, `skipRangeCheck = Members.Count > 1`, and the member-snapshot loop can each see different membership — e.g. a scan built with `skipRangeCheck=false` (solo) but `PreSorted=true` / member boxes populated, producing wrong partition/sort results in `SortAndCapGridCandidates`.

## Root Cause
Shared mutable list with no snapshot or lock between main-thread rebuild and background iteration.

## Fix
Snapshot Members (and the derived count) on the main thread when enqueueing the scan and pass the snapshot into `AsyncClusterScan`; or guard Members access with a lock. Snapshot preferred — no lock in the hot scan path.

**Resolution:** commit 422f124 (BuildId 260610.31) on `fix/v2.5.6` - RebuildClusters mutates cluster.Members under lock(cluster.Members); StartAsyncClusterScan snapshots membership on the main thread into _ScanMemberSnapshot under the same lock; all background-scan reads (memberCount, skipRangeCheck, member-box loop, profiler) use the snapshot.
