# BUG-261023.5: Floating-object collection still trusts the detached transport inventory (possible no-collect or item loss)

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-261023.1 #5 — `NanobotSystem.Collecting.cs:159-201` (`EmptyFloatingObject` :178, :185, :194); also `NanobotSystem.Inventory.cs:343` (`EmptyBlockInventories` → `TransferItemFrom` into the transport)

## Description
BUG-260827.2 found that `CanItemsBeAdded` returned false for `_TransportInventory` even when empty
and stopped trusting it on the weld path (direct volume headroom + verified add). The collect path still:
1. gates on `dstInventory.CanItemsBeAdded(...)` — if the engine still refuses, nothing is ever collected;
2. calls `MyFloatingObjects.RemoveFloatingObject(floating)` **then** an unverified `AddItems` — if the add
   is refused (partially), the items are destroyed (the BUG-260612.2 concern).
The constructor fix (explicit maxMass) *should* heal both, but that was never verified in-game (open
follow-up in BUG-260827.2) and the code is inconsistent with the weld path.

## Steps to Reproduce
1. BoundingBox BaR, drop SteelPlate stacks inside the area, CollectIfIdle off.
2. Watch `Items to collect` and the cargo; also grind a container with loot (EmptyBlockInventories path).

## Root Cause
Mitigation applied to the weld path only.

## Fix
Implemented (BuildId 261023.2).
- New helpers in `NanobotSystem.Inventory.cs`:
  - `AddItemsVerified(dst, amount, content)` — `AddItems` then returns the amount that actually
    landed (`GetItemAmount` before/after); never trusts `CanItemsBeAdded`.
  - `MoveItemVerified(src, itemId, definition, dst, amount)` — clamps to the source amount and the
    real volume headroom (`MaxVolume - CurrentVolume`, floored for integral items), adds first, then
    removes from the source only what landed.
- `EmptyFloatingObject` (`NanobotSystem.Collecting.cs`): the `CanItemsBeAdded` gate is gone; the add
  happens first and only the amount that landed is taken from the floating object (removed when fully
  taken, shrunk otherwise). A refused add leaves the floating object untouched — no item loss.
  Null-definition guard added (unknown item definition would have thrown).
- `EmptyBlockInventories` (grind loot, corpses): the engine `TransferItemFrom` stays first (it is
  atomic, so it cannot lose items); when it refuses, the item is retried with `MoveItemVerified`
  instead of stalling. `remainingVolume` uses the amount actually moved. Profile line gains
  `fallbackMoves=` — non-zero in-game means the engine still refuses on the detached inventory.
- Not done: no `Clone()` of the item content (not used anywhere in the mod and its whitelist status
  can't be checked at build time). Content is passed as-is, like the existing floating path; partial
  moves only happen for stackable items, whose content carries no mutable state.

Files: `NanobotSystem.Collecting.cs`, `NanobotSystem.Inventory.cs`; harness `S10_CollectFloating.cs` +
`ScenarioRegistry.cs`.

Verification: unit — `TransportInventoryMoveTests` (5: what-landed, refused add leaves the source
untouched, remove only what landed, headroom/source clamp, integral floor vs ore fractions). In-game:
pending — harness `test run S10` (5 × 100 SteelPlate floating stacks collected; asserts none left and
cargo + welder + transport == 500 exactly), and a manual grind of a loot-filled container (S04's target
grid has no inventories) checking `fallbackMoves` in the `EmptyBlockInventories` profile.
