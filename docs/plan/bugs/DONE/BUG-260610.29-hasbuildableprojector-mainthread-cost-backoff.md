# BUG-260610.29: HasBuildableProjectorOnGrid Phase 2 is expensive main-thread work every second and defeats FEAT-071 idle backoff

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `NanobotSystem.Scanning.Block.cs:125-175`, `NanobotSystem.Scanning.cs:105-116`

## Description
The comment sells it as "a cheap property read", but in BoundingBox mode Phase 2 executes on the main thread, once per second per idle coordinator: `GetTopMostEntitiesInBox` under `lock(MyAPIGateway.Entities)`, plus `GetTerminalSystemForGrid` + typed block enumeration for every grid in the area, plus `new HashSet<long>()` / `new List<IMyCubeGrid>()` allocations per call. With many grids in range this is a recurring main-thread spike.

Compounding it: if any projector reports `BuildableBlocksCount > 0` but the BaR can never actually build it (out of range, relation-blocked — only `IsProjecting`/count is checked here), `_consecutiveEmptyScans` is reset to 0 every second (Scanning.cs:113), so the FEAT-071 idle backoff never engages and the cluster scans at full rate forever. The `catch { }` at :175 also hides any failure.

## Root Cause
Per-second engine sweep on the main thread; buildability check too coarse to gate the backoff reset.

## Fix
Throttle Phase 2 (e.g. every few seconds), reuse `SharedEntityCache` for the entity query, log in the catch, and only reset `_consecutiveEmptyScans` when the projector is actually workable (range/relation checked) — or cap how often the projector check can reset the backoff.

**Resolution:** commit 422f124 (BuildId 260610.31) on `fix/v2.5.6` - BoundingBox phase of HasBuildableProjectorOnGrid throttled to 5 s (cached verdict in between, Phase 1 own-grid check stays at 1 s) and uses SharedEntityCache; backoff reset is one-shot per not-buildable-to-buildable transition (_projectorColdStartArmed); silent catch now logs. Build: Debug, 0 errors.
