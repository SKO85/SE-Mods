# BUG-261122.1: Projected blocks are no longer built since SE 1.211.018 — the game now requires the first component in the welder's own inventory

## Status: Fixed
## Severity: Critical
## Version: v2.5.6 (and a hotfix of the released v2.5.5 — see REVIEW-261122.1 questions)
## Found In: GitHub #149 (davidkuyt00-phx), #150 (Rl-Real45), PR #151 (Lejangt) — `NanobotSystem.Welding.cs:565-780` (`ServerDoWeld` projected path, `proj.Build` at :637)

## Description
Since the game hotfix 1.211.018 (2026-11-20, two days after Warfare 3 / 1.211.017) BaR systems in survival
weld hand-placed blocks normally but build projected blocks only now and then. They idle next to a projection
with buildable blocks; after a while they stop for good until the BaR (or the grid) is switched off and on.

## Steps to Reproduce
1. Survival, game 01_211_018. BaR with AllowBuild, stocked cargo, projector with a blueprint in range.
2. Optional, makes it near-certain: enable `PushComponentImmediately` (keeps the BaR block inventory empty).
3. Watch: few or no projected blocks appear. With DebugMode on (SP), the BaR terminal shows
   `ProjBuild: built=0 noBlock=N | last=builderInventoryEmpty`; the server log shows
   `projected build left no block; reason=builderInventoryEmpty; inBlockInventory=0; inTransport>=1`.

## Root Cause
`MyProjectorBase.BuildInternal` gained server-side checks in 1.211.018. In survival (unless an instant build
with creative tools) it now returns **without building and without an error** when the builder's inventory
holds less than 1 of `BlockDefinition.Components[0]`. For a ship welder the builder inventory is its block
inventory 0 (`MySpaceBuildComponent.GetBuilderInventory`). BaR stages the creation component in the detached
`_TransportInventory` and only checks that one (`:589`), so `proj.Build` is rejected. It works only when a
spare happens to sit in the block inventory at that moment (`ServerEmptyTransportInventory` parks transport
leftovers there between ticks, `ServerPickFromWelder` picks them back). Three rejections per block promote it
to the permanent skip list (BUG-120) — see BUG-261122.2 for why that turns into "stops for good".

Evidence:
- **1.210 (01_210_014, local Bin64, IL dump):** `BuildInternal` has no builder-inventory check (DLC check →
  `BuildBlockRequestInternal`). `GetBuilderInventory` returns `GetInventory(0)` for `MyShipWelder`.
  `TakeMaterialsFromBuilder` removes the build materials from that inventory only (the conveyor fallback is
  for characters in cockpits). This is also why 1.210 built blocks for free (BUG-261023.2 / PR #148).
- **1.211.018:** two independent decompiles agree — Lejangt (#149 comment, PR #151) and the Multigrid
  Projector plugin, commit `7d17f95` (2026-11-20, "Load on Space Engineers 1.211.018 and mirror its
  BuildInternal checks"): `BuildInternal` IL hash changed `f78ce8f7` → `b08d536e` between 1.211.017 and .018;
  the mirrored check is `SurvivalMode && !creativeToolsBuild && !BuilderHoldsFirstComponent(builder, def)`.
  The same hotfix also added a world-limit check and an RPC sender check to that method. None of this is in
  Keen's patch notes.
- Not yet checked against the 1.211.018 binaries directly (local install is still 1.210).

## Fix
Fixed in BuildId 261122.2, on `fix/v2.5.6` only (owner decision: ships with v2.5.6, no v2.5.5 hotfix).
- `3ab43cc` — PR #151 commit 1 cherry-picked with Lejangt as author (conflicts with BUG-261023.2 resolved:
  lend first, snapshot after the lend).
- Follow-up hardening, `NanobotSystem.Welding.cs`:
  - `ServerLendBuildComponent` (:597) / `ServerReturnBuildComponent` (:615) now use `MoveItemVerified`
    (BUG-261023.5) with the component definition from `Components[0]`; a null or refusing block inventory
    makes the lend fail cleanly (`buildComponentLend`, no `Build`, no skip count).
  - `ServerDoWeld` (:682 lend, :774 accounting): `engineTookCreation` is decided once right after `Build`
    (block-inventory amount dropped below the post-lend snapshot). An untaken lent piece goes back to the
    transport; the BUG-261023.2 transport charge (:810) only runs when the engine took nothing. The NRE and
    generic catch paths return the lent piece only if it is still there.
  - Profile: `ServerDoWeld` gains `lent=` and `engineTook=` next to `welderCompAtBuild=` / `creationCharged=`.
    Expected on 1.211.018 survival: `lent=True;engineTook=True;creationCharged=False`.
- Diagnostics from BuildId 261122.1 stay (see below).
- Tests: `ProjectedBuildComponentTests` (lend moves one piece, uses a piece already there, full inventory keeps
  the piece, creative moves nothing, return moves it back).
- Pending: in-game check on 1.211.018 (SCN-WELD-002 D/E) once the local game is updated.

Diagnostics (BuildId 261122.1):
- `ServerDoWeld` profile: `welderCompAtBuild=` (block-inventory amount of Components[0] at build time).
- Throttled server-log line (Error level, once per minute per BaR) when `proj.Build` leaves no block:
  `reason=builderInventoryEmpty|unknown`, inventory/transport amounts, `canBuild=` (`IMyProjector.CanBuild`
  result), projector counts, fails for that block. `reason=builderInventoryEmpty` must not appear after the fix;
  any `unknown` points at the other new 1.211.018 checks (world limits, RPC) or DLC.
- Debug panel (SP / listen server, DebugMode): `ProjBuild: built= noBlock= skipped= | last=`.

## Scenario
SCN-WELD-002 (new variant E: empty block inventory + `PushComponentImmediately`, game ≥ 1.211.018;
variant D accounting must still hold). In-game harness S03 (planned) should cover it.
