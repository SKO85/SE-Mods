# BUG-260824.9: Foreign-claimed lock-on block wastes whole weld ticks; BUG-260610.32 branch is dead code

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260824.1 — `NanobotSystem.Welding.cs:140`

## Description
When the lock-on block's assignment TTL expires and another BaR re-claims it,
`IsAssignedToOtherSystem` (line 140) `continue`s without clearing `State.CurrentWeldingBlock`
or setting `lookingForNext`, so the lock-on filter (lines 108-112) skips every subsequent
target and the whole weld tick is wasted — every tick, until the other BaR releases the block.
`lockOnFound` is already set (lines 127-132), so the vanished-lock-on retry (line 286) never
fires either.

The BUG-260610.32 mitigation (`refreshed == false` branch at line 238) is dead code for this
race: line 236 is only reached after line 140 passes, and assignment ops are main-thread, so
the state cannot change in between.

## Root Cause
Foreign-assignment check for the lock-on block lacks the release/clear/lookingForNext
handling that the grid-limit path (lines 225-229) has.

## Fix
In the `assignedToOther` branch: when the block is the lock-on, clear
`State.CurrentWeldingBlock` and set `lookingForNext = true` (no release — the claim belongs
to the other BaR), mirroring the grid-limit lock-on handling. Commit 48de267,
BuildId 260824.1. File: `NanobotSystem.Welding.cs:140`.
