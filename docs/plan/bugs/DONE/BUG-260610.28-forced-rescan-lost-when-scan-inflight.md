# BUG-260610.28: Forced rescans are lost when a scan is already in flight

## Status: Fixed
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `NanobotSystem.Scanning.cs:164, 393-410`

## Description
The coordinator path clears `_rescanForced = false` (:164) **before** calling `StartAsyncClusterScan`, which can return without enqueueing anything when `_AsyncUpdateSourcesAndTargetsRunning` is still true (:394/:407). The trigger (settings change, member starvation signal) is consumed but no scan is scheduled; the in-flight scan may have started before the state change it was meant to pick up. The intent degrades to ordinary cadence — for a user-driven `TriggerImmediateRescan(bypassDebounce: true)` the "immediate" rescan silently doesn't happen.

## Root Cause
Flag consumed before the enqueue is confirmed.

## Fix
Clear `_rescanForced` only after `StartAsyncClusterScan` actually enqueued (return a bool), or re-set the flag when the re-entry guard fires.

**Resolution:** commit 422f124 (BuildId 260610.31) on `fix/v2.5.6` - StartAsyncClusterScan returns true only when the scan was enqueued; the coordinator consumes _rescanForced only on true, so forced rescans survive the re-entry guard. Build: Debug, 0 errors.
