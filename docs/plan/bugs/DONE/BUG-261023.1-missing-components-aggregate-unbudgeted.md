# BUG-261023.1: Missing-components aggregate rebuild is unbudgeted, phase-aligned and repeated by every cluster member

## Status: Fixed
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-261023.1 #1 — `NanobotSystem.Welding.cs:1410-1519` (`ServerTryRebuildMissingComponentsAggregate`), call site `NanobotSystem.Operations.cs:66`

## Description
The BUG-260824.2 fix (GitHub #142) rebuilds `State.MissingComponents` every 3 s **per BaR** on the main
thread: `GetMissingComponents` on every non-ignored weld target (up to `MaxPossibleWeldTargets`, now 1024)
plus `GetItems` on the welder, transport and every connected source until the need is covered. It runs
outside the weld ms budget and has no cap. Three things make it spike:

1. `_NextMissingAggregateAt` starts at zero and advances from the tick it fired. BaRs in the same stagger
   group run `ServerTryWeldingGrindingCollecting` in the same frame (`cycle % effectiveGroups`), so their
   rebuilds fire in the **same frame every 3 s, forever**.
2. Cluster members each hold a near-identical copy of the coordinator's target list and each repeat the
   full walk — 5 co-located BaRs = 5x the same work, 50 BaRs = 50x.
3. With a shortage (need stays positive) the source subtraction walks every source inventory each time.

Estimate: ~2-10 µs per `GetMissingComponents` × 1024 targets ≈ 2-10 ms per BaR; 20 BaRs in one group ≈
40-200 ms in one frame every 3 s. This is new in v2.5.6 and lands exactly in the GitHub #143 scenario
(large base, many BaRs), so it must be fixed or proven cheap before release.

## Steps to Reproduce
1. Large base (1000+ damaged/projected blocks in range), 5-20 BaRs in one cluster, empty-ish cargo.
2. `/nanobars profile start 120 0` (or harness `test run S08 x5`).
3. `RebuildMissingComponentsAggregate` maxMs and its spacing; sim speed dips every 3 s.

## Root Cause
Aggregate correctness was prioritised over cost: no budget, no time slicing, no phase offset, no
sharing within a cluster.

## Fix
Implemented (BuildId 261023.1). The pass is now a small state machine
(`_AggPhase` 0 idle / 1 targets / 2 sources, `_AggCursor`):
- **Phase offset**: the first pass of each BaR starts `(EntityId & 0x7FFFFFFF) % 3000` ms after its
  first call; the next pass starts 3 s after the previous one *published*.
- **Time slice**: ≤ 128 targets per call (`MissingAggregateTargetsPerSlice`), then welder/transport
  stock, then ≤ 32 source inventories per call (`MissingAggregateSourcesPerSlice`), stopping as soon as
  the need is covered. Targets marked `Ignore` between slices are skipped. The previous list stays
  published until the pass completes (no flicker); with no targets the list clears at once.
- **Abort**: when the BaR stops being ready the unfinished pass is dropped (no target references
  kept while disabled) and the phase offset is re-seeded, so `systems enable all` doesn't re-align.
- **Global cap**: every slice claims `Mod.TryClaimAggregateSlice()` (`MaxAggregateSlicesPerTickDefault`
  = 4 → ≤ 512 target walks per tick across all BaRs); refused slices just wait for a later call.
- Not done: "skip when the target hash is unchanged" (stock can drop without a hash change, so it
  could hide a new shortage) and cluster sharing (members' areas differ). The cap bounds both.
- Profile line per call: `phase=a->b;targets;blocksWalked;sourcesWalked;published;missingKinds;deferred`.

Files: `NanobotSystem.Welding.cs` (`ServerTryRebuildMissingComponentsAggregate`,
`PublishMissingComponentsAggregate`, `AbortMissingComponentsAggregate`), `NanobotSystem.Operations.cs`
(abort when not ready), `NanobotSystem.cs` (pass fields), `Mod.cs` (slice budget).

Verification: unit — `MissingComponentsAggregateTests` (10 tests drive the real method with faked
blocks/inventories: slice size, publish once, stale list kept, global cap refusal, phase offset +
interval, stock subtraction, source slices, empty clear, Ignore mid-pass, abort + re-seed). In-game: pending —
S02 (list correctness) and S08 x5 (`RebuildMissingComponentsAggregate` maxMs ≤ 1, no 3 s sawtooth).
