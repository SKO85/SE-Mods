# BUG-261123.1: A starved BaR stops BaRs on other ships from repairing its blocks

## Status: Done
## Severity: Medium
## Version: v2.5.7 (bug in v2.5.6 and earlier)
## Found In: Discord #help-topics "One BAR will not Help another BAR" (the_kurgan, 2026-10-04); confirmed in code
`NanobotSystem.Welding.cs` failure branch -> `BlockFailureCooldownHandler.MarkFailed`

## Description
Ship A (damaged, BaR without components) and ship B (BaR with components), not docked. B's BaR often does not
repair A. When a BaR finds no components for a block it marks the block "failed" for every BaR for
`BlockFailureCooldownSeconds` (15 s). The handler assumes all BaRs share the same supply ("unavailable from every
source"); BaRs on separate conveyor networks do not. A's BaR keeps re-marking its blocks, B keeps skipping them.

## Steps to reproduce
Harness S86 (SCN-WELD-008).

## Expected behavior
B repairs A's blocks.

## Actual behavior
S86 on 261123.6: ship B repaired 5/10 of ship A's blocks in 45 s (first weld at 1.9 s); ship A's BaR stayed MissingComponents.

## Affected areas
`Handlers/BlockFailureCooldownHandler.cs`, `NanobotSystem.Welding.cs` (MarkFailed / IsOnCooldown).

## Fix (proposed)
Store the failing BaR's supply group with the mark and honour it only for BaRs in the same group: the BaR grid's
logical grid group (connectors / mechanical links; same conveyor network). One reference compare per check.

## Scenario
SCN-WELD-008 — ingame:S86 (new).

## Resolution
`BlockFailureCooldownHandler` stores the failing BaR's supply group (the BaR grid's logical grid group: connectors,
rotors, pistons = shared conveyors) as the mark; `IsOnCooldown(block, supplyGroup)` only matches the same group.
ServerTryWelding resolves the group once per call. Unit: BlockFailureCooldownTests. In game, BuildId 261123.7: S86
10/10 in 3.4 s (was 5/10 in 45 s); S01 / S02 / S05 green (same-ship behaviour unchanged).
