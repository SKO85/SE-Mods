# BUG-261123.5: MaxItemsAddable relies on CanItemsBeAdded, which refused ore in game (transport may stall)

## Status: Open
## Severity: Medium
## Version: v2.5.7
## Found In: REVIEW-261123.1 (profiler-driven performance review, 2026-11-23) — `Utils/UtilsInventory.cs:104` (MaxItemsAddable binary search), callers `NanobotSystem.Inventory.cs:251`, `Utils/UtilsInventory.cs:163/179`, `NanobotSystem.Welding.cs:1489`

## Description
In S89 `CanItemsBeAdded(amount, MyItemType.MakeOre("Iron"))` returned false for every amount, so a
`MaxFractionItemsAddable` search returned 0. The mod uses the same search to move items from the transport into the
welder, to push, and in the weld pull. A false 0 reads as "full" (pull: stops the source walk). S89's BaR stopped at
99 % with 873 kg of iron left in its transport, which this may explain. Components evidently work (all weld tests
pass); ore / ingots are the suspect.

## Fix (proposed)
First a probe scenario: transport holding ore, welder with room -> does the move happen; CanItemsBeAdded per item
class. If confirmed: compute the fit from free volume / item volume (as BUG-260827.2 already does) and verify the moved
amount afterwards. Remove the unused fractional AddMaxItems variant.
