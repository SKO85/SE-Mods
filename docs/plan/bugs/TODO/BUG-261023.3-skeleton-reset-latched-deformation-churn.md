# BUG-261023.3: SkeletonResetHandler re-resets every once-dented block forever and ignores the weld filters

## Status: Open
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-261023.1 #3 — `Handlers/SkeletonResetHandler.cs`, `NanobotSystem.Scanning.Block.cs:246-260`, `Extensions/SlimBlockExtensions.cs:47-56`

## Description
The scan enqueues a skeleton reset for any full-integrity block with `MaxDeformation > 0.01`. The
engine caches that value (`MySlimBlock.m_cachedMaxDeformation`, refreshed only by `UpdateMaxDeformation`)
— the code's own comment says it "doesn't reset until restart". So after the first reset the block still
qualifies; it is re-queued every time the 60 s per-block cooldown expires and
`ResetBlockSkeleton(block, updateSync: true)` runs again — skeleton work plus a network sync per block, for
every block ever dented within range, for as long as the BaR runs (capped at 2 per tick ≈ 120/s).

The enqueue also skips the filters every other weld action respects: ignore colour, weld priority
(class disabled), `WeldSkeleton` mode ("never repair existing blocks") and safe-zone welding permission.

## Steps to Reproduce
1. Dent 200 armor blocks (collision), weld them back to full.
2. Leave a BaR running near them; profile `SkeletonResetHandler.Process` for 5 minutes.
3. Resets continue every ~60 s per block although nothing is dented.

## Root Cause
Enqueue condition uses the latched `MaxDeformation`, and the reset path was added outside the normal
weld-target filter chain.

## Fix
Proposed (not implemented):
- Enqueue only when `block.HasDeformation` (already read on the scan thread inside `NeedRepair`).
- In `Process` (main thread) re-check `HasDeformation` before resetting; when false, stamp the cooldown
  and skip. Cap dequeues per tick (e.g. 16) so skips can't turn into a long main-thread walk.
- Apply the weld filters before enqueue: `!WeldSkeleton`, ignore colour, `BlockWeldPriority.GetEnabled`,
  `State.SafeZoneAllowsWelding`.
- Add `skippedNotDeformed=` to the profiler line.
