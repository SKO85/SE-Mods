# BUG-260612.1: Self-count uses raw grid id while GridSystemCount is keyed by effective id — projected lock-on self-eviction churn

## Status: Open
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-260612.1 #H1 — `NanobotSystem.Operations.cs:379-389`, `NanobotSystem.Welding.cs:204-218`

## Description
Regression interplay of BUG-260610.21 with BUG-160/164: `Mod.GridSystemCount` is now incremented/decremented under the EFFECTIVE grid id (projector parent for projected blocks), but `GetCachedSystemCountOnGrid` subtracts "self" by comparing the lock-on block's RAW `CubeGrid.EntityId` against the queried effective id. For a projected lock-on the ids differ, the subtraction never fires, and the BaR counts itself as another system. At the per-grid limit the lock-on re-check evicts the BaR's own legitimate lock-on, the setter decrements, next tick re-picks — weld/evict churn (~50% duty cycle at limit 1; mass eviction at saturation), and the grind picker refuses targets on that grid one BaR too early. Found independently by two review agents; verified against source.

## Root Cause
One consumer of `GridSystemCount` was not migrated to effective-id resolution.

## Fix
In `GetCachedSystemCountOnGrid`, compare using `GetEffectiveGridId(myWeldBlock)` (and the grind block analogously) instead of raw `CubeGrid.EntityId`.
