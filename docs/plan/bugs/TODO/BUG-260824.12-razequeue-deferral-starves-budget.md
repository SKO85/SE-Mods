# BUG-260824.12: Mechanical-raze deferral re-dequeued within the same drain — starves non-mech razes

## Status: Open
## Severity: Low
## Version: v2.5.6
## Found In: REVIEW-260824.1 — `Handlers/RazeQueueHandler.cs:135`

## Description
BUG-260612.20's mechanical-raze deferral re-enqueues a budget-rejected mech block into the
same queue while the drain loop counts deferrals against its 5-dequeue budget, so one drain
can dequeue the same blocked block repeatedly.

Failure: several destroyed pistons/rotors are queued. Per drain (every 10 ticks): the first
mech block claims the 1-per-tick mechanical slot; each subsequent mech dequeue fails
`TryClaimMechanicalGrindSlot`, is `Enqueue()`d to the back (dedup key freed at line 115 so
re-add succeeds), and — since `processed++` runs on every dequeue with no entry-count
snapshot — is dequeued again within the same `while (processed < 5)` loop. Most of the drain
budget cycles guaranteed-failing deferrals; destroyed non-mechanical blocks linger as visual
ghosts and mech raze throughput drops to 1 per drain.

## Root Cause
Deferral re-enqueue interacts with a budget counted per dequeue, no per-drain entry snapshot.

## Fix
Snapshot the queue count at drain start and bound the loop by it; or stop dequeuing further
mech blocks once the per-tick mech slot is spent (peek-and-skip), keeping deferrals out of
the processed budget.
