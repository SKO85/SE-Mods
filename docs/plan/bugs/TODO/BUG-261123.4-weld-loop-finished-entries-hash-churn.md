# BUG-261123.4: Weld loop handles finished entries expensively and changes the state hash every walk

## Measured (detail run S43 / S70, BuildId 261123.34) — loop part minor
Finished / ignored entries: 0.5 (S43) and 1.9 (S70) per call — small. The lock-on walk passes ~27-33 entries per call
before reaching the locked block, but each is four field compares (cheap). The state-hash / sync part cannot be
measured in single player (no clients: every TryTransmitState is "notNeeded"); needs a DS / Torch run. Priority: low
until the DS data shows extra state messages.

## Status: Open
## Severity: Low
## Version: v2.5.7
## Found In: REVIEW-261123.1 (profiler-driven performance review, 2026-11-23) — `NanobotSystem.Welding.cs:140-295`

## Description
Entries that are already finished / ignored still go through three lookups and a `ChangeHash` on every walk.
The state fingerprint then changes on every pass, which on a dedicated server likely forces more state messages
(older Torch data: state sync ~2-2.6 ms/s).

## Fix (proposed)
Skip finished / ignored entries first, before lookups and before touching the hash.

## Scenario
SCN-BUDGET-006 — ingame:S43, S64, S65 (weld-loop ms/s); DS check of state messages (see FEAT-261123.4).

Recommendation: close without a change; revisit only if a server shows state sync high in a profile.
