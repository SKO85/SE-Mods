# BUG-260610.5: NeedRepair() mutates the grid (ResetSkeleton) from the background scan thread

## Status: Open
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Extensions/SlimBlockExtensions.cs:44-57`, `NanobotSystem.Scanning.Block.cs:221`

## Description
`NeedRepair()` is documented as pure ("Pure functions — no caches, no per-instance state") but mutates the grid: when `MaxDeformation > MinDeformation` or `HasDeformation` it calls `ResetSkeleton()` → `MyCubeGrid.ResetBlockSkeleton(cg.GetCubeBlock(block.Min), true)` / `block.FixBones(0, 100f)`. It is called from `AsyncAddBlockIfWeldTarget` (`Scanning.Block.cs:221`), which runs on the background scan pool. These engine calls touch grid skeleton, bones, and render/physics update queues and are not thread-safe — racing the main thread (which also calls `NeedRepair` from `NanobotSystem.Welding.cs:431` on the same blocks) risks corruption or hard crashes on DS under load. Additionally, since `MaxDeformation` never resets in-game (per the code comment), every deformed block re-triggers `ResetBlockSkeleton` on every scan pass (~2 s), repeatedly and pointlessly.

## Root Cause
Grid mutation embedded in a predicate that is invoked from both main-thread and background-thread paths.

## Fix
Remove the mutation from the scan path: either queue `ResetSkeleton` to the main thread (`MyAPIGateway.Utilities.InvokeOnGameThread`) or perform it only from the weld loop call site. Keep the predicate itself read-only.

## Reinvestigation (2026-06-10)

**Still valid.** Call sites unchanged: `Scanning.Block.cs:238` (background scan pool) and `Welding.cs:462` (main thread) both call `NeedRepair`, which mutates via `ResetSkeleton()` → `MyCubeGrid.ResetBlockSkeleton(...)` / `FixBones` — skeleton/bone/render state the engine does not synchronize.

**Key subtlety the original fix sketch missed:** the two deformation branches are a player-visible *deformation repair* feature, and they behave differently:

- `HasDeformation` branch returns **true** → block becomes a weld target → the weld loop's own `NeedRepair` call re-runs the reset on the main thread anyway. Removing the scan-side mutation costs nothing here.
- `MaxDeformation > 0.01` branch returns **false** (full integrity, just deformed — the in-code comment notes `MaxDeformation` never clears in-game). Such blocks are *never added as weld targets*, so the scan-side `ResetSkeleton` is the **only** thing that ever visually repairs them. Naively making the predicate pure silently kills deformation repair for this whole class of blocks.

**Recommended fix:**

1. `NeedRepair(this IMySlimBlock, AutoWeldOptions, bool allowMutate)` — weld loop passes `true` (inline reset stays; it's already on the main thread), scan passes `false`. Verdict logic unchanged.
2. When the scan path hits either deformation branch with `allowMutate == false`, enqueue grid+position into a new main-thread skeleton-reset queue modeled on `RazeQueueHandler`: deduped by `BlockSystemAssigningHandler.BlockKey`, budgeted (~5 resets per drain), drained from `Mod.UpdateBeforeSimulation`. The dedup also fixes the second half of this ticket — today a permanently-deformed block re-triggers `ResetBlockSkeleton` on every scan pass (~5 s), forever.
3. Clear the queue in `Mod.UnloadData` (same treatment RazeQueueHandler got in BUG-260610.11).

**Alternative rejected:** `MyAPIGateway.Utilities.InvokeOnGameThread` per block — allocates a closure per deformed block per scan, no dedup, unbounded per-frame work when a battle-damaged grid has hundreds of deformed blocks.

Severity stays **High** — engine-state corruption / DS crash class under load.
