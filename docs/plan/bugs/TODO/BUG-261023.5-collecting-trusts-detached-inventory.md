# BUG-261023.5: Floating-object collection still trusts the detached transport inventory (possible no-collect or item loss)

## Status: Open
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-261023.1 #5 — `NanobotSystem.Collecting.cs:159-201` (`EmptyFloatingObject` :178, :185, :194); also `NanobotSystem.Inventory.cs:343` (`EmptyBlockInventories` → `TransferItemFrom` into the transport)

## Description
BUG-260827.2 found that `CanItemsBeAdded` returned false for `_TransportInventory` even when empty
and stopped trusting it on the weld path (direct volume headroom + verified add). The collect path still:
1. gates on `dstInventory.CanItemsBeAdded(...)` — if the engine still refuses, nothing is ever collected;
2. calls `MyFloatingObjects.RemoveFloatingObject(floating)` **then** an unverified `AddItems` — if the add
   is refused (partially), the items are destroyed (the BUG-260612.2 concern).
The constructor fix (explicit maxMass) *should* heal both, but that was never verified in-game (open
follow-up in BUG-260827.2) and the code is inconsistent with the weld path.

## Steps to Reproduce
1. BoundingBox BaR, drop SteelPlate stacks inside the area, CollectIfIdle off.
2. Watch `Items to collect` and the cargo; also grind a container with loot (EmptyBlockInventories path).

## Root Cause
Mitigation applied to the weld path only.

## Fix
Proposed (not implemented):
Mirror ServerPickFromWelder: replace `CanItemsBeAdded` with a direct headroom check
(`MaxVolume - CurrentVolume >= amount × volume`), add first and verify with `GetItemAmount` before/after,
and only then remove/shrink the floating object by the amount actually added. Verify grind loot and
collection in-game (S04 + a collect scenario).

## Scenario
SCN-COLLECT-001, SCN-GRIND-001 (S04)
