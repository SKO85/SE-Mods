# BUG-260612.7: GridScanCache shared across home grids while grind filters are home-grid-dependent — shield bypass / false protection

## Status: Open
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-260612.1 #H7 — `NanobotSystem.Scanning.Block.cs:278, 340-343`, `NanobotSystem.State.cs:72`, `Cluster/GridScanCache.cs:36-43`

## Description
`ComputeScanParamsHash` deliberately excludes the home-grid EntityId so same-settings coordinators share cache entries — but the grind filter's results depend on the home grid: own-grid blocks skip `IsBlockProtected` (`State.cs:72-73`) and skip the off-grid autogrind shield gate (`Scanning.Block.cs:278`). Two coordinators with matching hashes scanning the same target grid T:

- **Bypass:** BaR A sits ON shielded grid T → its candidates (own-grid exempt) get cached → off-grid BaR B consumes them and grinds a shielded grid (up to 3 s per entry, refreshed while A keeps scanning).
- **False protection (reverse order):** B scans T first → all candidates rejected (shielded) → cached empty → A on its own grid won't grind it despite being exempt.

Preconditions are narrow (same owner+settings, matching `IsShielded`, multi-member cluster) but it's a real protection inversion in both directions. The weld side has no home-grid-dependent filter and is unaffected.

## Root Cause
Cache key ignores a filter input (target grid == home grid).

## Fix
Factor "target grid is the scanner's home grid" into the cache lookup — e.g. skip the cache when `targetGridId == Welder.CubeGrid.EntityId`, or mix that bit into the per-target-grid key.
