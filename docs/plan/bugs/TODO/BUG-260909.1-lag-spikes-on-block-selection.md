# BUG-260909.1: Lag spikes and sim-speed drop when a BaR selects a new block (GitHub #143)

## Status: Open
## Severity: High (user-facing, server stability)
## Version: v2.5.6
## Found In: GitHub issue #143 (FoIsense, 2026-09-09) — reported against released v2.5.5

## Description
Server-side report: on bases above ~3000 blocks, sim-speed drops from 1.0 to ~0.3 while
BaRs are active, with fluctuating spikes down to ~0.2. The reporter attributes each spike
to the moment a BaR "selects a new block to build", and says it got worse after a recent
update (mod v2.5.5 shipped 2026-06-09; the SE 1.210.x game updates are also in scope —
the reporter did not say which update they mean).

No profiling data supplied yet. Sustained 1.0 → 0.3 and intermittent spikes to 0.2 are
two different problems and may have different causes; do not assume one root cause.

## Steps to Reproduce
Not reproduced locally. Reporter's setup: dedicated server, base > 3000 blocks, BaRs
actively welding. BaR count, SearchMode, and settings unknown.

## Information Needed From Reporter
- `/nanobars version` (mod version + BuildId) and the SE game version.
- Which update made it worse (mod update vs game update, approximate date).
- `/nanobars config list` — especially `MaxWeldMsPerTick`, `MaxGrindMsPerTick`,
  `MaxGrindsPerTick`, `StaggerGroupCount`, `MaxSystemsPerTargetGrid`.
- `/nanobars systems count` — how many BaRs, and whether they are clustered.
- Per-block `SearchMode` (BoundingBox on a 3000-block base is far more expensive than Grids)
  and `WorkMode`.
- A profiling session during the spikes: `/nanobars profile start 120 5`, then `profile stop`.

## Notes — prior art, do not re-derive
Per-selection cost was profiled in the v2.5.4/v2.5.5 cycle and is largely **engine** cost:
- BUG-105: grind `decreaseMs` 5-12 ms (grid integrity recalc + conveyor refresh on full
  dismount); weld `buildMs` 7-9 ms (`proj.Build` on projected blocks). Friendly-damage-loop
  hypothesis refuted.
- BUG-108: projected -> physical resolve ~2.5 ms per newly selected target.
- BUG-122: `ServerFindMissingComponents` 9-10 ms on projected blocks; ~15 ms unaccounted in
  the `ServerTryWelding` loop body (instrumentation added).
- BUG-106/.107: global dismount and `proj.Build` budgets (cap 3/tick) to spread that cost.
- BUG-126/.129: welder-full source walk causing constant (not periodic) spikes.
- `MaxWeldMsPerTick` / `MaxGrindMsPerTick` (default 8 ms, global) bound total per-tick work;
  they do not make a single engine `Weld()` call cheaper.

All of the above is already in the reporter's v2.5.5 build.

## Suspects To Check On v2.5.6 Before Blaming v2.5.5
- `ServerTryRebuildMissingComponentsAggregate` (`NanobotSystem.Welding.cs:1410`, added for
  BUG-260824.2): walks up to `MaxPossibleWeldTargets` (1024) targets calling
  `GetMissingComponents` plus every connected source inventory, every 3 s per BaR, on the
  main thread, outside the weld ms budget. `_NextMissingAggregateAt` starts at zero so BaRs
  can align on the same tick. Unprofiled at scale — this is new cost in exactly this
  scenario and must be measured before v2.5.6 ships.
- `SkeletonResetHandler` (BUG-260827.1) — budgeted, but new main-thread work.
