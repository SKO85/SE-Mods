# BUG-260610.2: Server applies client block-settings messages without ownership/access check

## Status: Open
## Severity: High
## Version: v2.5.6
## Found In: REVIEW-260610.1 — `Handlers/NetworkMessagingHandler.cs:258-273`

## Description
The server branch of `MsgBlockSettingsReceived` (MSGID_BLOCK_SETTINGS_FROM_CLIENT, 40103) ignores the tamper-proof `sender` parameter and looks up the block purely by the client-supplied `msgRcv.EntityId`, then applies, persists (`Settings.Save`) and rebroadcasts the settings. No check that the sender owns, has terminal access to, or has factional rights on the target block. Vanilla terminal access is enforced only client-side, so a modified client can forge this message for any BaR on the server: set an enemy's BaR to GrindOnly, change grind color to the owner's paint, widen/zero its area, enable janitor grinding, etc. `SettingsChanged()` → `CheckLimits()` clamps ranges but does nothing about identity.

## Steps to Reproduce
Forge a `MsgBlockSettings` (40103) with another player's BaR EntityId from any client; server applies it.

## Root Cause
Handler trusts payload `EntityId`; `sender` is unused.

## Fix
Resolve the sender's identity from `sender` (SteamId) and validate access against the block (ownership/relation, e.g. `welder.HasPlayerAccess(identityId)` or ownership-relation check) before `AssignReceived`. Reject + log on failure.

## Reinvestigation (2026-06-10)

**Still valid.** The server branch of `MsgBlockSettingsReceived` still applies/persists/rebroadcasts purely by payload `EntityId`. The fixes shipped since filing don't close it: BUG-260610.3 guards only the *client* branch (`fromServer`), BUG-260610.18 clamps values, BUG-260610.31 rate-limits to one apply per 500 ms per block — a forger can still reconfigure any BaR, just at most twice per second.

**Recommended fix (concrete, ~25 lines in `NetworkMessagingHandler.cs`):**

1. Extract the player lookup already used by `IsRemoteAdmin` (:163-185) into a `TryGetPlayerBySteamId(ulong, out IMyPlayer)` helper (same `GetPlayers` walk, reuse the `_adminCheckPlayers` scratch — handler runs on the main thread).
2. In the server branch, after the rate limit: accept when `UtilsPlayer.IsAdminLevel(player.PromoteLevel)` (admins may edit any block — matches the command channel's authority model and keeps admin tooling working); otherwise require `system.Welder.HasPlayerAccess(player.IdentityId)` — the engine's own ownership/share gate, so faction share, share-all and unowned-block semantics match the vanilla terminal exactly.
3. Reject path: return without applying and log at Error with sender + EntityId (no response message — don't give a forger an oracle; the 500 ms rate limit already bounds log spam).
4. Sender not found among connected players (disconnected mid-flight): reject — fail closed.

**No legit-play regression:** vanilla already blocks non-owners from opening the terminal, so legitimate clients only send settings for blocks they can access; the listen-server host never hits this path (applies locally as server).

**Optional follow-up hardening (same helper, lower priority):** `ServerMsgBlockDataRequestReceived` replies with any block's settings/state to any requester — an information leak (area size, work mode, janitor config of enemy BaRs). The same access check could gate it.
