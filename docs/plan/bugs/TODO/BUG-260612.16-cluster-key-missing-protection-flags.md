# BUG-260612.16: Cluster key omits SafeZoneAllowsBuildingProjections and IsShielded — mixed-permission members share a coordinator's filtering

## Status: Open
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260612.1 #M9 — `Cluster/ScanClusterCoordinator.cs:227-229, 277-279`, `NanobotSystem.Scanning.Block.cs:365-370`

## Description
The cluster key/hash includes `SafeZoneAllowsWelding/Grinding` but not `SafeZoneAllowsBuildingProjections` or `State.IsShielded`, while the per-system scan-params hash includes both. Same-grid BaRs that differ only in those states share a cluster and inherit the coordinator's filtering: a projections-prohibited member can receive (and weld — no execution-time recheck, and `projector.Build`'s engine check keys off the projector grid, not the welding BaR) projected candidates from a permissive coordinator; on a grid partially inside a shield ellipsoid, members with differing `IsShielded` inherit the coordinator's off-grid autogrind filtering. Narrow, but inconsistent with the scan-hash treatment.

## Root Cause
Cluster key not kept in sync with scan-relevant state (same forward-compat rule as BUG-260511.9/.11).

## Fix
Add both flags to `ComputeClusterKey` and `ComputeClusterKeyHash` (same pattern as the existing SZ flags).
