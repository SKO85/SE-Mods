# BUG-260824.8: Per-block 500 ms settings rate limit silently drops a second client's change

## Status: Open
## Severity: Medium
## Version: v2.5.6
## Found In: REVIEW-260824.1 — `Handlers/NetworkMessagingHandler.cs:318`

## Description
BUG-260610.31's 500 ms rate limit is keyed per-block (`system._lastClientSettingsAppliedAt`),
not per-sender, and drops the second authorized client's settings message with a bare return —
the change is permanently lost, not delayed.

Failure: two faction members have the same BaR terminal open. A changes a flag at t=0; B
changes weld priority at t=0.3 s. B's message passes the access check but hits the window and
is dropped silently. B's client already cleared its dirty bit on transmit
(`SyncBlockSettings.GetTransmit`, `Changed & ~1u`, line 661) so `IsTransmitNeeded` never
resends, and the broadcast triggered by A's accepted message reverts B's UI.

## Root Cause
Rate limit designed against a single spamming client applied per-block, combined with
client-side dirty-bit clearing on transmit (no retry).

## Fix
Key the limit per (block, senderSteamId); or on rejection re-request/re-broadcast so the
sender's client re-marks dirty and retries after the window.
