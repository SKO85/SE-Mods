# BUG-260909.2: Bare catches in PeriodicMaintenanceScheduler hide maintenance failures

## Status: Open
## Severity: Low
## Version: v2.5.6
## Found In: REVIEW-260511.1 finding #3 (was tracked as the never-written BUG-260502.5)

## Description
REVIEW-260511.1 finding #3 flagged swallowed runtime exceptions in three places. Two are
now fixed: `BackgroundTaskQueue` logs task failures (BUG-260610.15) and
`NetworkMessagingHandler` logs send/receive failures (BUG-260610.41). The third,
`PeriodicMaintenanceScheduler`, still swallows everything:

`Managers/PeriodicMaintenanceScheduler.cs`
- `:65-69` — `InventoryHelper.Cleanup()`, `BlockPriorityHandling.GetItemKeyCache.CleanupExpired()`,
  `BlockFailureCooldownHandler.Cleanup()`, `SharedGridBlockCache.Cleanup()`,
  `SharedEntityCache.Cleanup()`, each `try { ... } catch { }`
- `:83` — `BlockSystemAssigningHandler.Cleanup()`
- `:151`, `:156` — the generic `work()` dispatch (sync and background paths)

A cache whose cleanup throws every cycle grows unbounded and nothing is ever logged, so
the symptom would surface only as a slow memory/perf leak with no trace of the cause.

## Root Cause
Defensive bare catches added so one failing maintenance task cannot take down the tick.
Keeping the isolation is right; discarding the exception is not.

## Fix
Replace each bare `catch { }` with a logged catch (`Logging.Level.Error`), keeping the
per-task isolation so one failure still cannot abort the rest of the cycle. Wrap the log
call itself in a bare catch, as `BackgroundTaskQueue.cs:123` does, so logging can't throw
out of maintenance.

Keep it minimal — no restructuring of the scheduler.
