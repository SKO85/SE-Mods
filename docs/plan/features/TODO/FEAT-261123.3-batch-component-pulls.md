# FEAT-261123.3: Pull more components per conveyor transfer

## Status: In progress
## Priority: Low
## Version: v2.5.7+

## Summary
Pull more components per conveyor transfer.

## Motivation
`TransferItemFrom` is 88 % of the pull cost, about one pull per welded block.

## Design
Pull 4-8x the current need into the BaR's own inventory per transfer (bounded by volume). Roughly halves the pull
cost (0.5-2.5 ms/s). Behaviour change (BaRs hold more stock; interacts with push options and other BaRs' supply) —
owner decision needed.

## Testing
SCN-INV-001 — ingame:S103-S110 (pull ms/s, plates conserved), S86, S90-S93.
## Owner decision (2026-11-23)
Re-measure the pull cost first (S105 / S106 `detail` on a build with BUG-261123.6, which cut weld attempts ~20x), then
decide. Only if the pull still costs a noticeable share: a bounded variant (2-4x the need, capped by free volume, only
from well-stocked sources).

## Measured before (S105 / S106 detail, 261123.51) and decision
~2 conveyor transfers per welded block; TransferItemFrom 0.20 ms (300 containers) / 0.40 ms (600) = 89-91 % of the pull
cost, ~8 / ~20 ms per second while 50 / 100 BaRs weld. Owner: do it (cautious variant). Note: the nanobot delivery wait
(S64: 42 % of cycles) is per block and stays; the gain is conveyor transfer cost.

## Implementation (261123.53)
`TryPullFromSource`: from a source holding plenty, transfer the block's need plus `PullBatchExtra` (up to 2 more blocks'
worth, `PullBatchFactor` = 3) into the BaR's inventory; the block's need moves on to the transport as before, the rest
stays in the BaR's inventory (picked first for the next blocks; other BaRs can still pull it). Limits: at least twice the
extra stays in the source; none while PushComponentImmediately is on; extra stock <= 10 % of the BaR's volume and only
while the BaR is below half full. Profiler: PullFromSourcesOnePass `extraPulled`. Unit: PullBatchTests.
