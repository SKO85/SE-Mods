# REVIEW-261123.1: Performance review from profiler measurements

## Status: Open (findings triaged into tickets; fixes pending)
## Date: 2026-11-23
## Scope: main-thread and background cost of the mod, from harness profiler summaries (S08, S43, S64-S70, S99-S102,
S103-S108) and the hot-path code; game 1.211 API behaviour (CanItemsBeAdded)

## Summary
The mod is light on the main thread: 0.19 ms per tick (1.1 %%) in S08, 0.30 ms (1.8 %%) in S43, ~0.63 ms (3.8 %%) with
20 BaRs, 0.82 ms (4.9 %%) with 40 BaRs (S70). 55-87 %% of the weld / grind path is engine work (`proj.Build`,
`IncreaseMountLevel`, `DecreaseMountLevel`, `TransferItemFrom`); every 10-23 ms spike is one engine call, bounded by the
existing budgets. The mod-owned share is ~2-12 ms/s under load. Scans run on a background thread at ~1.1 µs per block,
~95 %% of it mod code.

## Nanobot BaR: performance review based on profiler measurements

Analysis only. No repository files were changed.
Data: `test-<Sxx>-r1.NanobotProfiler.Summary.log`. Most runs are build 261122.27 / 261122.16 (v2.5.6). S99–S102 are build 261123.20 (v2.5.7).
Supporting evidence (with care, see 4.3):

### 0. How to read the numbers

- **Timings are inclusive.** `UpdateBeforeSimulation10_100` contains `ServerTryWeldingGrindingCollecting`, which contains `ServerTryWelding` and `ServerTryGrinding`, which contain `ServerDoWeld`/`ServerDoGrind` and `ServerFindMissingComponents`, which contains `PullFromSourcesOnePass`. Likewise `AsyncClusterScan` contains `AsyncAddBlocksOf*`, `PreSort*`, `SortAndCap*` and the coordinator's own `ApplyClusterResultToSelf`. `AsyncApplyClusterResults` contains the members' `ApplyClusterResultToSelf`. "Self" costs below are parent minus measured children.
- **Thread.**
  - Main thread: `UpdateBeforeSimulation10_100` and everything below it, `Mod.UpdateBeforeSimulation`, `RazeQueueHandler.Process`, `ImmediateRescanTrigger`.
  - Background (`Mod.AddAsyncAction` → `MyAPIGateway.Parallel.StartBackground`): `AsyncClusterScan`, `AsyncApplyClusterResults`, `ApplyClusterResultToSelf`, `AsyncAddBlocksOf*`, `PreSort*`, `SortAndCap*`, `AsyncScanForSources`, `AddIfConnectedToInventory`, `SharedGridBlockCache.*`.
  - Background work only costs the tick through lock contention, CPU competition and GC.
- **Share of tick** means main-thread ms per second ÷ 60 (ms per tick), as a percentage of 16.67 ms. Sim speed was 1.0 in all of these runs.
- **"steady" is not meaningful for scan methods.** Warm-up is the first 20 calls per method across all BaRs. Scan methods often have fewer than 20 calls (S64 `AsyncClusterScan`: 11 calls, 0 steady). For per-BaR methods steady ≈ all calls.
- **Profiler overhead.** In non-detail harness runs MinDuration is 10000 ms, so no per-call lines are written and the overhead is one `lock` + string dictionary lookup per `StopAndLog` (~0.1–0.3 µs). `Weldable` ran 35,661 times in S70, which adds roughly 5–10 ms to its parent `ServerTryWelding`.

#### 1.4 What this says

1. **Engine dominates the main thread.**
   - `ServerDoWeld` is 59–87 % of the weld path; `ServerDoGrind` is 54–82 % of the grind path.
   - In the `proj` detail log `ServerDoWeld` was 68 % `proj.Build` and 30 % `IncreaseMountLevel`; for non-projected blocks `mountMs` was 97.5 %. `stockpileMs`, `canContinueMs` and `integrityCheckMs` were all ≤ 0.009 ms.
   - Every main-thread spike of 10–23 ms is a single engine call:

     | Spike | Same as | Engine call |
     |---|---|---|
     | UBS10_100 max (S43, S64, S68–S70) | ServerDoWeld max | IncreaseMountLevel |
     | S67, S70 | ServerDoGrind max | DecreaseMountLevel |
     | S65 (14.4 ms) | `PullFromSourcesOnePass` max 13.8 ms | `TransferItemFrom` |
2. **What the mod can reduce on the main thread** is roughly the weld and grind loop self costs plus pull and transfer counts: about 2–12 ms/s in the load scenarios, 5–25 % of the mod's main-thread time. The grind loop self cost is the largest single mod-owned item and the most anomalous (0.04–0.11 ms per block for a list walk).
3. **Background:** the scan per-block filter (1.1 µs/block, which matters for #143-sized bases) and `ApplyClusterResultToSelf` (up to 13 ms/s CPU in S70, plus allocations).

### 2. Proposals (ranked by expected gain ÷ risk)

#### P1: Grind picker re-walks dead entries every tick (main thread, highest mod-owned item)

**Code**
- `NanobotSystem.Grinding.cs:74-141`. Every walk visits every entry before the first live one. For each entry it does:
  - `CubeGrid`
  - `FatBlock.Closed`
  - `IsGridOverSystemLimit`: HashSet plus `ConcurrentDictionary` lookup
  - `IsAssignedToOtherSystem`: BlockKey plus `ConcurrentDictionary` plus play-time read
  - `IsFullyDismounted`
  - for dismounted entries, `RazeQueueHandler.Enqueue` again (`:139`). The dedup key is dropped as soon as Process dequeues it (`RazeQueueHandler.cs:127`), so the same razed armor position is re-queued on later walks and RazeBlocks is called again for an empty cell.
- Removal propagation covers only the grinding BaR's own cluster (`RemoveGrindTargetEverywhere`, `:331-358`). Blocks razed by other clusters stay in a list until that cluster rescans.
- The rescan is delayed because `IsTargetListSaturated` (`NanobotSystem.Scanning.cs:250-262`) counts a dismounted armor block (`FatBlock == null`) as live. A list full of dead armor looks "saturated", so scans are skipped (FEAT-075, up to 60 s).

**Evidence**
- Grind loop self is 0.04–0.11 ms per ground block. That is far more than one walk of a few live entries.
- The per-block self cost is about the same in S66 (2 clusters, 90 µs) and S67 (10 clusters, 78 µs). All rigs overlap all ships, so most of each list is razed by other clusters. This fits a stale-entry walk better than the in-cluster fan-out.
- **Hypothesis, not yet measured:** the summary cannot show entry counts. The detail line already logs `iterations`, `skipDestroyed`, `skipClosed`.

**Change (minimal)**
- In the walk, check a per-entry flag first: `if (targetData.Ignore) continue;`. `TargetBlockData.Ignore` is unused by the grind lists today.
- When an entry is found dismounted or closed, set `Ignore = true`, enqueue the raze once and move on. Later walks then pay one field read for that entry.
- Optional: compact the list under the lock already held when the dead count exceeds, say, 32.
- `IsTargetListSaturated`: on the grind side count `!t.Ignore && !t.Block.IsFullyDismounted`; on the weld side count `!t.Ignore`. Lists of dead work then trigger a rescan instead of a 60 s skip.

**Expected:** 50–80 % of grind loop self, about 1–5 ms/s in S66–S70 (5–10 % of the mod's main-thread time). Fewer pointless RazeBlocks calls inside `RazeQueueHandler.Process` (0.4–0.7 ms/s).

**Risk:** low. A fully dismounted block is razed anyway, and a closed FatBlock can never come back. The saturation change makes scans more frequent (background) when lists are mostly dead.

**Verify**
- `test run S66,S67,S70 detail`: `iterations`/`skipDestroyed`/`skipClosed` per `ServerTryGrinding` call, before and after.
- `RazeQueueHandler.Process` `totalRazed` vs blocks ground.
- Target: (`ServerTryGrinding` − `ServerDoGrind`) / ground blocks ≤ 0.02 ms.
- `groundPerSecond` must not drop.
- Unit test: a walk over a list with N dismounted entries enqueues each once and touches no assignment cache on the second walk.

#### P2: Scan per-block filter, 1.1 µs/block (background, S99–S102, #143 bases)

Path for an intact, undamaged non-projected block (`NanobotSystem.Scanning.Block.cs:789-858` → `AsyncAddBlockIfTarget` `:37` → `AsyncAddBlockIfWeldTarget` `:260`):

1. `block.GetColorMask()`, always (`:267`), even when no colour option is on.
2. `block.IsProjected(out projector)` (`:269`): cast plus `Projector` per block. This is constant per grid.
3. `NeedRepair(WeldOptions, false)` (`SlimBlockExtensions.cs:33-66`):
   - `IsDestroyed`, `FatBlock`, `GetRequiredIntegrity` (`MaxIntegrity`, definition cast), `Integrity`, `MaxDeformation`
   - then **`HasDeformation`** for every intact block. The code comment says "heavy though". **Hypothesis:** it is a grid-skeleton bone lookup (around 27 dictionary probes for a 1×1×1 block) and the largest part of the 1.1 µs.
4. When `NeedRepair` is false, the deformation `else if` (`:318-324`) re-reads `IsDestroyed`, `Integrity`, `GetRequiredIntegrity` and `MaxDeformation`.
5. `TraverseConnectedGrid` (FatBlock null exits fast), a second `FatBlock` read, `ShouldStopScan`.
6. Relation, priority and `IsInRange` run only for blocks that pass `NeedRepair` (BUG-112 ordering). That part is fine.

**Change (cheapest first)**
- (a) **Gate `HasDeformation` on `MaxDeformation > 0f`.** A pristine block has `MaxDeformation == 0`, and a latched one is already returned by the `> MinDeformation` branch. Expected: a large share of the 1.1 µs (hypothesis). Risk: medium. If the engine does not restore `MaxDeformation` after a world reload while bones are still dented, such blocks would no longer be found by the scan. Check in game: dent a block, save and reload, read `MaxDeformation`/`HasDeformation`.
- (b) **Fuse `NeedRepair` and the deformation `else if`** into one classification (needs weld / latched dent / nothing). It reads each engine property once. Risk: none.
- (c) **Hoist per-grid invariants out of the block loop:** `IsProjected` (the projected grid already has its own branch at `:824-849`), `State.SafeZoneAllowsWelding`, `Settings.Flags` and `WeldOptions` as locals.
- (d) Read `GetColorMask()` only when `useIgnoreColor || useGrindColor`, and only after the integrity checks.
- (e) Grind side (`:346-419`) when janitor mode is on: `BlockGrindPriority.GetEnabled` and `GetUserRelationToOwner` run for every block before any cheap test. Put the integrity-ratio test first for `DisableOnly`/`HackOnly`, and memoise the relation per (grid, `block.OwnerId`) for one grid pass. `IsBuiltByOwnerOrFaction` remains per block.

**Expected:** (b)–(d) about 10–20 %; (a) possibly 50 % or more. Measure before claiming.

**Verify**
- S99–S102, `AsyncAddBlocksOfGrid` µs per block, target ≤ 0.5 µs.
- SCN-WELD-006 (skeleton reset) plus an in-game check that a dented block is still repaired.
- Add a profiling-only accumulated sub-timer for the `NeedRepair` call per grid pass (see gaps).

#### P3: Per-grid candidate cache that survives between scans (background, big static bases)

`GridScanCache` (`Cluster/GridScanCache.cs`) has a 3 s TTL and is cluster-only. A solo BaR next to an unchanged 10k-block base pays the full 11.5 ms every ~6 s (S102: 8 scans in 47 s).

**Change**
- Make the position-independent candidate list cacheable for solo BaRs too: cache before the range test, then run `IsInRange` on the cached candidates.
- Key validity on `GridChangeHandler.ChangedSince(gridId, cachedAt)` (damage and block-added stamps already exist) plus a longer safety TTL (e.g. 30 s) instead of 3 s.

**Expected:** scans of unchanged grids drop from O(blocks) to O(candidates): S102 11.5 ms → < 1 ms.

**Risk: medium.** Changes that do not stamp the grid stay stale up to the TTL:
- repaint (ignore/grind colour)
- ownership or faction change
- a new projection on the grid (`DropColdStartGridCaches` covers the cold start only)
- priority edits are already in `paramsHash`.

Welding progress is safe: finished blocks are filtered at execution by `Weldable`.

**Verify:** S99–S102 (second and later scans), S06 relation scenarios, colour scenarios, projector cold-start scenario, S08.

#### P4: Weld picker handles already-ignored entries the expensive way (main thread)

`NanobotSystem.Welding.cs:103-296`. For a non-lock-on entry that is already `Ignore = true` (completed), the walk still does:
- `IsAssignedToOtherSystem` (`:144`)
- `BlockFailureCooldownHandler.IsOnCooldown` (`:169`)
- then the `else` branch (`:282-295`): `ReleaseAssignmentIfEnabled` (a third lookup) and **`State.PossibleWeldTargets.ChangeHash()` on every walk**.

The repeated `ChangeHash` makes `possibleWeldTargetsChanged` true (`NanobotSystem.Operations.cs:249`), which:
- calls `State.HasChanged()`
- changes the transmit fingerprint (`:601`), so on MP/DS a full `MsgBlockStateSend` goes out each interval instead of backing off. In old Torch DS data `MsgBlockStateSend` cost ~0.21–0.25 ms per send and 1.9–2.6 ms/s. The SP harness cannot see this.

The first release on the Ignore transition is kept (BUG-048 still satisfied).

**Change:** right after the lock-on skip (`:112-116`), add `if (!isLockOnBlock && targetData.Ignore && (Settings.Flags & ScriptControlled) == 0) { skippedByIgnore++; continue; }`.

**Expected:** part of the weld loop self (0.9–5.7 ms/s). The size depends on the `skipIgnore` counts in a detail run; the `proj` run had few targets and is not representative. Plus fewer state sends on DS.

**Risk:** low. Claims on long-ignored blocks are no longer re-released each walk; they were released when the flag flipped, and the TTL covers the rest. This is consistent with BUG-053's "keep the claim on a failed projected build".

**Verify**
- Detail run S43/S64/S70: `skipIgnore`, `assignOpsMs`, `inLockMs`.
- Unit test: two walks over a list with ignored entries leave `CurrentHash` unchanged on the second walk.
- DS run: count of `TryTransmitState action=send`.

#### P5: Fewer conveyor transfers per welded block (main thread, engine-bound)

**Evidence**
- `PullFromSourcesOnePass` costs 1.0–4.7 ms/s; S65 max 13.8 ms, which was the S65 tick spike.
- In `proj` detail, `transferMs` (`TransferItemFrom`, `Welding.cs:1499`) was 88 % of pull time. `getItemsMs` and `maxItemsAddMs` were around 0.003 ms each.
- One pull happens per new block (S64: 775 pulls for 775 blocks).

**Change:** pull K × the need (e.g. K = 4–8) into the BaR's own inventory. Pulled items already land there, and `ServerPickFromWelder` (0.004 ms) serves the following blocks. Bounds:
- cap at e.g. 50 % of free welder volume
- disable when `PushComponentImmediately` is set (otherwise items ping-pong)
- optionally cap by `_AggMissingNeed` for that component.

**Expected:** fewer `TransferItemFrom` calls, so Pull −50 % or more (≈0.5–2.5 ms/s in S43/S64/S65), and fewer conveyor-path spikes.

**Risk: medium, behaviour change.**
- Components sit in BaR inventories.
- Must stay below the 98 % `InventoryFull` latch.
- Interacts with BaRs-as-sources (S103) and the companion-script missing list. It stays consistent because the aggregate already subtracts welder stock.

**Verify:** S43/S64/S65 Pull calls and ms/s, `ServerPickFromWelder` calls go up, `weldedPerSecond` must not drop; S103 (plates conserved), S89, S86, S02.

#### P6: `RemoveGrindTargetEverywhere` scans member lists back-to-front

`NanobotSystem.cs:176` iterates from the end. Cluster members share the coordinator's sort order, so the block just ground sits near the front. In a 10-member cluster that is up to 9 × 256 entry compares per ground block.

**Change:** iterate forward (it returns after the first hit).

**Expected:** about 10–15 µs per ground block in 10-member clusters (the S66 vs S67 difference is ~12 µs).

**Risk:** none. **Verify:** S66/S70 grind loop self; add a profiling marker (see gaps).

#### P7: Power check once per cycle; measure it first

`PowerHelper.HasRequiredElectricPower` (`Helpers/PowerHelper.cs:18`) runs in both `ServerTryWelding` (`Welding.cs:63`) and `ServerTryGrinding` (`Grinding.cs:47`), so twice per cycle in WeldBeforeGrind. It calls `MyResourceDistributorComponent.MaxAvailableResourceByType`. Its cost is **unmeasured**; it is suspected but not proven.

**Change:** compute once in `ServerTryWeldingGrindingCollecting` and pass it down, or memoise for ~1 s.

**Risk:** none (power availability changes slowly; BUG-261122.9 / FEAT-261122.3 untouched).

**Verify:** sub-timer first. Implement only if the call costs more than ~5 µs.

#### P8: Faction reputation path runs on every grind call (unmeasured, PvP servers)

`NanobotSystem.Grinding.cs:254-264` → `UtilsFaction.DamageReputationWithPlayerFaction` on every grind call against a foreign-owned grid (`DecreaseFactionReputationOnGrinding` is true by default). It costs:
- `UtilsPlayer.GetPlayer` (`Utils/UtilsPlayer.cs:24-33`): allocates a list and enumerates all players
- two faction lookups
- `MyVisualScriptLogicProvider.Get`/`SetRelationBetweenPlayerAndFaction`. The setter is a reputation change and likely a replicated event.

No harness scenario covers it: S66–S70 grind derelicts with owner 0, which skip the path.

**Change:** accumulate the −5 per (welder owner, target faction) and apply once per ~2 s. Use a reusable player list.

**Risk:** low; the total reputation loss stays the same.

**Verify:** add a grind-enemy-faction scenario with a marker on the call.

#### P9: Smaller items (each < 1 ms/s)

- **`UpdateCustomInfo` on DS** (`NanobotSystem.CustomInfo.cs:19-49`), 0.1–0.5 ms/s. Server-side custom info is not replicated; clients rebuild their own (`Update.cs:326-330`). Skip it when `IsDedicated`. Risk: PB scripts on DS that parse `DetailedInfo`; the companion script does not.
- **`RebuildMissingComponentsAggregate`** (`Welding.cs:1630`), 0.3–0.9 ms/s. Members of a cluster rebuild nearly the same 512-target aggregate. Possible fixes: a longer cadence when the list hash and source set are unchanged, or a shared cluster aggregate (display semantics change). Low priority.
- **`GetGridGroup(Logical)` per `ServerTryWelding` call** (`Welding.cs:43`): only needed for the cooldown check and mark. Compute it lazily. Microseconds.
- **Disabled or not-initialised BaRs** still pay ~1.3 µs per Update10 (seen in `proj`: 102k calls, 0.43 ms/s). Matters only with hundreds of disabled BaRs.

#### P10: `ApplyClusterResultToSelf` (background CPU and GC)

Costs 1.6–13.2 ms/s, avg 0.3–2.0 ms, max 17.8 ms (S69). Each member does the following for every cluster candidate, up to 512 × 16:
- full `IsInRange` (`Scanning.cs:1016`): engine `ComputeScaledHalfExtents`, grid `WorldMatrix`, `GridIntegerToWorld`, OBB SAT test
- `new TargetBlockData` (`:1018`) before truncation to 512

### 3. CanItemsBeAdded / MaxItemsAddable dependencies (SE 1.211)

`UtilsInventory.MaxItemsAddable` (`Utils/UtilsInventory.cs:104-123`) does one full-amount probe and then a binary search: up to ⌊log2 n⌋ + 1 extra `CanItemsBeAdded` calls. If `CanItemsBeAdded` answers false for every amount (as seen for a hand-made ore `MyItemType`), it silently returns 0 after ~log2(n) engine calls. For an ore stack of 5,000 that is about 13 calls per item per attempt.

Callers:

| Caller | Type used | Effect if it returns 0 |
|---|---|---|
| `NanobotSystem.Welding.cs:1489` (`TryPullFromSource`) | **hand-made** `MyDefinitionId` (component) converted to `MyItemType` | 0 is read as "welder full" and **aborts the whole source walk** (`:1491-1495`). Components currently work in the harness, but the code has the risky shape. |
| `NanobotSystem.Inventory.cs:251` (`ServerEmptyTransportInventory`) | `item.Type` from `GetItems` | items stay in the transport |
| `Utils/UtilsInventory.cs:163, 179` (`TryTransferItemTo`, push) | `srcItem.Type` | nothing pushed → `_PushTargetsFull` latch |
| `MaxFractionItemsAddable` via `AddMaxItems` / `AddMaxItemsWithCheck` (`:194-240`) | `objectBuilder.GetObjectId()` | – (no remaining external callers; candidate dead code) |

Proposal: use the same pattern as BUG-260827.2 — `min(amount, floor((MaxVolume − CurrentVolume) / volume))` from one property read, then verify the moved amount by delta (the transfer return value / `GetItemAmount`). That removes the binary search and the false "welder full" abort.

#### 4.1 Missing markers or sub-timers

- client `Effects.UpdateEffects` (every second frame per BaR)
- the per-block scan split: a profiling-only accumulated tick count for `NeedRepair`, relation and `IsInRange` per grid pass, logged in the `AsyncAddBlocksOfGrid` line.

#### 4.2 Harness and summary limits

- **The harness is single-player.** `TryTransmitState` returns early (`!MultiplayerActive`), so `MsgBlockStateSend` serialisation and engine replication (block integrity sync, stockpile events, reputation events) are never measured. Old Torch data shows ~2–2.6 ms/s for state sends alone. A DS run of S64/S70 is needed.
- **`Mod.UpdateBeforeSimulation` includes the harness `TestTick`** (`Mod.cs:648`). Its 5.7–6.7 ms maxima (S43, S66, S68) cannot be attributed. Profile `TestTick` separately.
- **No per-frame total.** The summary gives per-call max, but sim speed depends on the sum of all BaRs in one frame. `Mod.RecordTickCost` covers only `Mod.UpdateBeforeSimulation`. Add a frame accumulator over all main-thread entry points with frame max and p99 in the summary.
- **Spikes cannot be correlated.** Detail lines use `DateTime.UtcNow.ToString("u")`, which has 1 s resolution (`MethodProfiler.cs:732`). Isolated 4–8 ms maxima on otherwise ~1–70 µs methods (`UpdateCustomInfo` 7.5, `Weldable` 4.3, `ImmediateRescanTrigger` 6.4, `Mod.UBS` 6.7) may be GC or OS pauses rather than method cost. Logging a frame number plus Stopwatch ms would show simultaneous spikes. Whether `GC.CollectionCount` is whitelisted is unverified.
- **Warm-up is the first 20 calls globally**, not time-based. Scan methods often have 0 steady calls (S64, S99–S102). Use "exclude the first N seconds" instead.
- **Thread is not tagged.** Domain summaries mix main and background (`Utility`/`Scan`). Tag the thread per method name in the summary.
- **No "why idle" counter.** 52 % of S70 BaR-cycles did no weld or grind (6,200 cycles vs 1,415 + 1,552 operations), and the summary cannot say why: budget refusal, exhausted skip, assignment or grid limit. `ServerTryWelding`/`ServerTryGrinding` should log a slot-refused flag. Today it is only inferable from `welding=False;needWelding=True;compChecks=0`.

#### 4.3 Profiler side effects

- In **detail** runs (MinDuration 0) every child `StopAndLog` writes a formatted line under `_syncRoot` inside its parent's timer. This inflates parents: in `proj`, `ServerTryWelding inLockMs` averaged 43 µs for ~10 entries. Use detail runs for counters and sub-timer ratios only, and summaries for totals.
- `FlushAll` (background, every 5 s) holds `_syncRoot` during file flushes (`MethodProfiler.cs:757-767`). Main-thread `StopAndLog` calls wait on it during detail runs, adding spikes to parents.
