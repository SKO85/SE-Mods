## Findings

Severity-ordered. "Verified" = re-checked against the cited source lines after the agent pass.

### Critical

1. **Session-relative static timers never reset on world unload — scans and periodic maintenance can go dead after a world switch.** *(verified)*
   `Mod.cs:240-242` (`_LastSourcesAndTargetsUpdateTimer`, `_LastSyncModDataRequestSend`), `PeriodicMaintenanceScheduler.cs` (all static `PeriodicTask.LastRun`), `GridOwnershipCacheHandler.cs:30`, `FriendlyRelationsHandler.cs:38`, `Mod.cs:97-98` (`_cachedAutoStaggerFrame`), `Mod.cs:139` (`SimSpeedOverride`).
   These statics hold `ElapsedPlayTime`/frame values and `Mod.UnloadData()` (Mod.cs:441-503) resets none of them. Loading a world with lower play time than the previous one (same game process) makes every `now - lastRun >= interval` gate false until the new world's play time catches up: `RebuildSourcesAndTargetsTimer` (Mod.cs:618) never fires → all BaRs idle; all periodic maintenance (ownership cache, TTL cleanups, assignment cleanup, friendly-relations rebuild) dead; auto-stagger frozen; admin sim-speed override leaks into the next world. Needs a static `ResetSessionState()` called from `UnloadData`/`LoadData`.

### High

2. **Server applies client block-settings messages without any ownership/access check.** *(verified)*
   `NetworkMessagingHandler.cs:258-273` (`MsgBlockSettingsReceived`, server branch). The handler ignores the tamper-proof `sender` arg and trusts the payload `EntityId`: any modified client can reconfigure any BaR on the server (set enemy BaR to GrindOnly, widen area, enable janitor grind, change grind color, …), and the server persists + rebroadcasts it. Validate `sender` against ownership/terminal access before `AssignReceived`.

3. **Client message handlers don't check `fromServer` — forged client→client messages accepted.** *(verified)*
   `NetworkMessagingHandler.cs`: `ClientMsgModSettingsReceived` (:185), `ClientMsgBlockStateReceived` (:204), `ClientMsgModCommandResponseReceived` (:229), and the client branch of `MsgBlockSettingsReceived` (:274-284). The newest handlers (`ClientMsgDebugStatsReceived` :383, `ClientMsgProfileSummaryReceived` :406) do guard with `if (!isSenderServer) return;` — the four older ones need the same. A malicious client can overwrite a victim's local `Mod.Settings`, desync their UI, or pop arbitrary chat/mission screens.

4. **Safe-zone precheck ignores zone radius and caps at 2 zones — grinding-protection bypass.** *(verified)*
   `SafeZoneHandler.cs:212-241` (`GetSafeZonesInRange`): precheck is `Distance(gridCenter, zoneCenter) > range` with fixed `range = 300` and `take = 2`. Zone radius is never added, so a large zone (vanilla up to 500 m) whose center is >300 m away but engulfs the grid is filtered before the precise test; result `zoneId = 0` is then cached 15 s → BaR grinds inside an active safe zone. The `take = 2` cap fails similarly with 3+ nearby zones. Use `distance > range + z.Radius` and remove/raise the cap.

5. **`NeedRepair()` mutates the grid (`ResetSkeleton`) from the background scan thread.** *(verified)*
   `SlimBlockExtensions.cs:44-57` calls `ResetSkeleton()` → `MyCubeGrid.ResetBlockSkeleton(...)` / `FixBones`. Called from `AsyncAddBlockIfWeldTarget` (`NanobotSystem.Scanning.Block.cs:221`) which runs on the background pool. Engine skeleton/bones/render calls are not thread-safe → corruption/crash risk on DS; also re-triggers every ~2 s scan for permanently-deformed blocks. Mutation must be queued to the main thread or restricted to the weld loop (`NanobotSystem.Welding.cs:431`).

6. **`Init()` early-return retry path: duplicated event subscriptions and half-initialized block visible to mod-wide iteration.** *(verified)*
   `NanobotSystem.Init.cs:118-192`: registration in `Mod.NanobotSystems` (:128) and event subscription (`_onEnabledChanged += lambda`, `_Welder.EnabledChanged += _onEnabledChanged`, :143-158) happen before the `welderInventory == null` early return (:161-162) that leaves `_IsInit = false`. The 10-frame retry then appends another lambda and re-subscribes the accumulated multicast each attempt (O(N²) handler invocations), and `Mod.SettingsChanged()`'s second loop (Mod.cs:370, no try/catch) can NRE on `_TransportInventory == null` (Init.cs:74), aborting settings fan-out for remaining BaRs. `Close()` is fully gated on `_IsInit` (:201), so such a block also never unregisters. Move the early-exit checks before registration/subscription; make `Close()` unregister even when `!_IsInit`.

7. **`GetSyncList()` enumerates target lists without the lock — races the background scan swap during state serialization.** *(verified; found independently by two reviewers)*
   `Collections\TargetBlockDataHashList.cs:12-23`, `TargetEntityDataHashList.cs:12-23`, invoked via `SyncBlockState.*Sync` getters (`SyncBlockState.cs:344-436`) during ProtoBuf serialization in `MsgBlockStateSend`. The background scan clears/refills the same lists under `lock` (`Scanning.cs:1182-1224`). Concurrent enumeration throws `InvalidOperationException` or serializes torn data; the exception is swallowed without logging (`NetworkMessagingHandler.cs:509-515`) → silently dropped state packets / client desync. Take the list lock in `GetSyncList()` (or snapshot under lock before serialize), and log in the catch.

8. **`SharedEntityCache` key is lossy — wrong/missed entity results in BoundingBox mode.** *(verified)*
   `SharedEntityCache.cs:34` keys by box *center* only (50 m quantized) — a small solo box and a kilometre-scale cluster discovery box with nearby centers share one slot; whoever writes first serves the other wrong results for 4 s (silently missing grids). Additionally `QuantizePosition` (:81-98) is a multiplicative hash, not bit-packing as commented: cells `(qx, qy+1, qz-31)` collide exactly with `(qx, qy, qz)` (~1.5 km apart). Include quantized extents in the key and actually bit-pack the coordinates.

9. **`_ActiveWorkingEffects` counter leaks on particle-creation failure — all weld/grind effects can become permanently disabled client-side.** *(verified)*
   `Effects.cs:158-165`: `_ActiveWorkingEffects++` happens before `TryCreateParticleEffect`; the decrement (:141-146) only fires when `_ParticleEffectWorking1 != null`. Each failed creation drifts the static counter up; at `MaxWorkingEffects` (150) no BaR shows effects for the rest of the session. `SetTransportEffects` (:370-379) already has the correct increment-on-success pattern — mirror it.

10. **Projected blocks get the 15 s global failure cooldown when they merely lose the proj-build budget race.** *(agent-verified)*
    `NanobotSystem.Welding.cs:542-553` (proj-build gate `TryClaimProjBuildSlot`, cap 3/tick) returns false without marking "budget-deferred"; if transport already completed, the caller's else-branch (:343-357) clears lock-on, releases the assignment, and calls `BlockFailureCooldownHandler.MarkFailed` — embargoing the buildable block for every BaR for 15 s. In multi-BaR shipyards this throttles projection throughput far below the budget's intent. Handle like the weld-slot budget path (:297-305): keep lock-on, retry next tick.

### Medium

11. **Static handler state holding game objects never cleared in `UnloadData` — cross-world leaks and stale-state corruption.** *(verified that UnloadData clears only BlockSystemAssigning/BlockFailureCooldown/ClusterCoordinator/SharedGridBlockCache/SharedEntityCache)*
    Not cleared: `FriendlyRelationsHandler._BaRsByOwner/_DamageByOwner`, `RazeQueueHandler._queue/_pendingKeys` (next world's first `Process()` razes blocks from the dead world / wrong grid on EntityId reuse), `GridOwnershipCacheHandler.Cache/GridLastAccess` (TTL is session-clock based → entries look unexpired in the new world; EntityId collision returns wrong ownership relation), `Mod.GridSystemCount` (stale counts → false saturation), `BlockPriorityHandling.GetItemKeyCache`, `GridScanCache` (also: `Invalidate()` has no callers; `MaybeCleanup` only runs from `Set` when Count ≥ 32 → closed-grid `IMySlimBlock` refs pinned indefinitely once scanning stops).

12. **`NanobotSystem.Close()` doesn't release the system's block assignments.** `Init.cs:199-273` — claims live up to `AssignmentTtlSeconds` (≤30 s) after the BaR is destroyed, blocking other BaRs. One-liner: `BlockSystemAssigningHandler.ReleaseAllForSystem(_Welder.EntityId)` (already used elsewhere).

13. **`ScanCluster.Members` (plain `List<NanobotSystem>`) mutated on main thread while background scans iterate it.** `ScanClusterCoordinator.cs:87-113` (clusters reused, `Members.Clear()/Add()`) vs `Scanning.cs:437,463,479-488` (three separate `Count` reads + indexed access on the worker). Can throw `ArgumentOutOfRangeException` (swallowed → scan lost) or build a scan with inconsistent membership. Snapshot Members on the main thread before enqueueing.

14. **Member saturated-skip blocks fresh members from applying an already-published result.** `Scanning.cs:131-138` vs `168-174`: a newly placed/re-enabled member in a saturated cluster returns early even though `publishedResult` is applicable → BaR idles up to `MaxScanSkipDuration` (60 s). Honor the skip only when there is no newer published result.

15. **Background workers swallow all exceptions (`catch { }` with no logging); pending queue survives unload.** `BackgroundTaskQueue.cs:84` + `Mod.cs:448-456` (1 s drain timeout, queue never purged, workers can repopulate caches after unload-clear). Recurring scan failures are invisible; stale actions can run against the next world. Log in the catch, purge the queue on unload, add a shutting-down flag.

16. **`PriorityHandling` list mutated on main thread without `_hashLock` while background `UpdateHash` enumerates it.** `PriorityHandling.cs:281-307` vs mutators (:134-158, 178-189, 219-223, 248-273). Player reordering priorities mid-scan → swallowed `InvalidOperationException` (lost scan) or torn priority hash. Mutators should take `_hashLock` (cheap, rare).

17. **Per-client block-data request consumes the global dirty flag / delta hashes — other clients miss updates.** `NetworkMessagingHandler.cs:96-115` + `SyncBlockState.GetTransmit` (:521-590): delta-sync state is per-block, not per-recipient; one client's targeted request suppresses the pending broadcast and advances list hashes for everyone.

18. **`CheckLimits` doesn't clamp NaN/negative `AreaSize`/`AreaOffset`.** `SyncBlockSettings.cs:696-728` — one-sided `>` clamps only; forged NaN/negative values survive the server-side re-clamp, persist, broadcast, and poison `RecalcAreaBoundigBox()`/scanning.

19. **Server replies to client-supplied `SteamId` instead of tamper-proof `sender` in data requests.** `NetworkMessagingHandler.cs:86-94, 96-115` — forged requests direct payloads at arbitrary players and trigger finding 17 "for" someone else.

20. **Culture-sensitive `float.TryParse` in chat commands.** `ConfigCommand.cs:419`, `SimCommand.cs:28` — on comma-decimal locales `"2.5"` parses as 25 (in-range, silent). Use `InvariantCulture`.

21. **`MaxSystemsPerTargetGrid` not counted for pre-materialization projected blocks.** `SyncBlockState.cs:186-195, 234-243` increments `Mod.GridSystemCount` with the projected grid id while the limit checks resolve to the projector's parent grid id (`Operations.cs:489-496`). During component transport, unlimited BaRs can lock onto one projection. Inc/Dec should use `GetEffectiveGridId`.

22. **Collecting holds the target-list lock across engine inventory transfers / entity deletion.** `Collecting.cs:30-50` — stalls a background scan worker on publish (same contention BUG-135/137 removed for weld/grind). Pick targets under lock, do engine work outside.

23. **Weld path mutates shared scan state outside the lock.** `Welding.cs:327` (`ChangeHash()` — non-atomic `CurrentHash++` racing the scan's `RebuildHash`) and `targetData.Ignore/Block` writes in `ServerDoWeld` race the scan's ignored-block preservation pass (`Scanning.cs:1185-1204`). All other `ChangeHash` call sites are inside the lock. Take the lock briefly around the post-weld updates.

24. **`DamageHandler.OnAfterDamage` does an O(all BaRs) walk + faction-relation calls per grind-damage event.** `DamageHandler.cs:112-131` — hundreds of engine relation calls/s on busy servers; `FriendlyRelationsHandler` already maintains this data on a 15 s rebuild — consume it.

25. **`Effects.Close()` never removes the light from `MyLights`.** `Effects.cs:438-443` — pooled render-light slot leaks per BaR closed while actively working; `SetWorkingEffects` (:150) shows the correct teardown.

26. **MethodProfiler stop/write race truncates session log files.** `MethodProfiler.cs:474-501, 739-757` — `StopAndLog` checks `IsEnabled` outside `_syncRoot`; an in-flight call after `CloseInternal()` reopens the same filename via `WriteFileInLocalStorage` (truncates the finalized log) and leaks an open writer. Re-check `_isRunning` inside `GetOrCreateWriter`.

27. **`SafeZoneHandler`/`DamageHandler.Unregister` latch `_registered = true` forever if `Session` is null at unload.** `SafeZoneHandler.cs:136-153`, `DamageHandler.cs:41-51` — next world's `Register()` no-ops (no zone events / no character-damage protection). Reset the flag and clear collections unconditionally.

28. **Forced rescans lost when a scan is already in flight.** `Scanning.cs:164` clears `_rescanForced` before `StartAsyncClusterScan`, which can no-op on the re-entry guard (:394-410) — `TriggerImmediateRescan` silently degrades to normal cadence. Clear the flag only after the scan was actually enqueued.

29. **`HasBuildableProjectorOnGrid` Phase 2 is expensive main-thread work every second and defeats FEAT-071 idle backoff.** `Scanning.Block.cs:125-175` — `GetTopMostEntitiesInBox` under the entities lock + per-grid terminal enumeration + allocations, once per second per idle coordinator; an unworkable-but-buildable projector resets `_consecutiveEmptyScans` forever (`Scanning.cs:113`). Also `catch { }` hides failures.

## Recommendations

- Fix order: finding 1 (session reset) + 2/3 (network auth) + 4 (safe zone) + 5 (thread-unsafe grid mutation) first — they are the cheapest fixes with the highest impact (a static reset method, `sender`/`fromServer` guards mirroring the existing newest handlers, radius-aware precheck, moving `ResetSkeleton` to the weld loop).
- Findings 6, 7, 9, 11, 12 are small, mechanical, low-risk patches.
- Findings 8, 10, 13, 14 need a little design care (cache key shape, budget-deferred signaling, member snapshotting, saturated-skip bypass) but are still contained.
- All recommendations are allocation-neutral or allocation-reducing; nothing here adds work to hot paths.
